## 1 简介

您接好一个 SPIMCI 模块，发出一次读取，它成功了。事务完成，确认应答存在，数据也返回了。

但模块并没有上电。

SPIMCI 将 ACK 编码为 **00h**（B.3.7.1.2），因此全零是一个有效的确认应答，后面跟着全零数据。
Binho 在实验台上正好复现了这种情况：读取完成，看到了确认应答，数据为 `00 00`。
一次完成的 SPIMCI 事务本身绝不能作为模块存在的证据。

本笔记以一种静默无法伪造的方式启动调试 SPIMCI 链路，并顺带解决 SPIMCI 给主机带来的第二个问题。

### 1.1 范围

## 3 SPIMCI 是什么，以及为什么值得理解它

SPIMCI 在 CMIS 5.3 中引入，由共封装光学推动；修订历史中写有"SPI-based SPIMCI in support of CPO"。
字符串 `SPI` 在 CMIS 5.2 中从未出现。

它也是对未来任何绑定都至关重要的先例。它的加入完全没有触及寄存器访问层或 Common Data Block，
而且在加入的同时修正了寻址方式。I2CMCI 只携带页内字节地址，因此需要 00h:126 和 00h:127 处的页选择寄存器；
而 SPIMCI 事务携带完整的存储体、页和字节三维地址，具有隐式页切换，并且最多可传输 2048 字节。

这对主机的实际意义是：**没有需要写入的页选择寄存器，也没有可能出错的跨事务地址状态。**

Table: 规范固定的参数

| 参数 | 值 | 出处 |
|---|---|---|
| 字长 | 8 位，最高有效位在前 | B.3.7.2.3 |
| 采样边沿 | CLK 上升沿 | B.3.7.1 |
| 片选极性 | 低电平有效 | B.3.3 |
| 最大传输量 | 2048 字节 | B.3.7.1 |

> **注**：规范规定了采样边沿，但从未说明 CLK 的空闲电平，因此"SPIMCI 是 SPI 模式 0"是一种推断，
> 而不是引文。该工具默认使用模式 0，并允许选择模式。

## 4 事务结构

每个 SPIMCI 事务都是 **4 + N + M** 字节，分为三个阶段。

Table: 事务控制阶段，4 字节，仅从发起方到目标器件

| 位 | 字段 | 说明 |
|---|---|---|
| 0 | Command Type，R/Wn | 见第 5.2 节 |
| 1:4 | Bank Index | 4 位。规范指出这"不允许大于 15 的任意存储体索引值" |
| 5:15 | EncodedSize | 11 位。传输字节数 = EncodedSize + 1，最大 2048 |
| 16:23 | Page Index | 8 位 |
| 24:31 | Byte Index | 8 位，起始地址。此后顺序递增 |

在整个控制阶段，`IITO` 均未定义。

**流控阶段，N 字节，N 至少为 2。** 发起方发送零值的虚拟字节，目标器件忽略这些字节。
目标器件在该阶段的**最后一个**字节中，通过 `IITO` 返回 **ACK = 00h** 或 **NACK = FFh**。

**数据传输阶段，M = EncodedSize + 1 字节。** 读取时，数据在 `IITO` 上，`IOTI` 上发送 00h。
写入时，数据在 `IOTI` 上，`IITO` 未定义。

## 5 两个未知量，以及如何确定它们

### 5.1 N 不在线路上传输，而且存在自举漏洞

`N` 由 `00h:213` 位 6-0 处的 `MciFlowControlDuration` 和 `00h:213` 位 7 处的
`MciFlowControlDurationEncoding` 推导得出：

Table: 流控字节数

| 编码位 | 推导方式 |
|---|---|
| 0，静态 | N = 2 + 通告值 |
| 1，与速率相关 | N = max(2, ceil(duration x SpiSpeedInMHz / 8))，速率取自 `00h:27.3-0` 处的 `MciSpeedConfiguration` |

B.3.7.1.2 要求双方以完全相同的方式推导 `N`。但在已知 `N` 之前无法读取 `00h:213`，而规范没有给出安全的自举值。
被动的总线观察者同样无法知道它。

解决方法是扫描 `N`，让模块自身的校验和来判断哪个值是正确的，这正是 `spi-probe` 所做的事情。

### 5.2 R/Wn 极性自相矛盾

Table: CMIS 5.3 中的 R/Wn 极性

| 出处 | 规定 |
|---|---|
| B.3.7.1.1 | "该位为 1 时，表示请求读取" |
| B.3.8.1 至 B.3.8.5，图 B-14 至 B-17 | 0 表示读取 |

两者都在同一份文档中。有一个值得了解的判定依据：B.3.8.5 将 **TEST** 定义为从字节地址 0 进行的一字节读取，
并且**全部 32 个控制位均为零**，只有当 0 表示读取时，这才是自洽的。该工具默认遵循图示，
可按要求使用任一极性，在未指定时会探测两种极性。

## 6 流程

### 6.1 离线确认工具

```
python cmis_mci.py selfcheck
```

### 6.2 确定 N 和极性

```
python cmis_mci.py spi-probe --transport spi
```

该命令针对每种极性将 `N` 从 2 扫描到 16，并且**仅**在 Page 00h 校验和验证通过时才接受某个组合：
即 94 字节的模块特定内容与模块自己写入的一个字节相符。一次完成的事务、一个确认应答，
甚至看似合理的数据，都可能由未上电的电路板产生。

> **注意**：未上电的电路板也可能产生匹配的校验和，而且只有一种方式，恰恰是实际中会出现的那种方式。
> 静默的 SPI 总线对每个字节都返回 `00h`。九十四个 `00h` 字节之和为 `00h`，而同一总线报告的存储校验和也是 `00h`，
> 因此二者一致。所以，只有当校验和验证通过**并且** Page 00h 包含不止一个不同的值时，扫描才会接受某个组合。
> 第 8.2 节记录了加入该条件之前命令的报告内容。

如果这些值已知，请直接传入并跳过扫描：

```
python cmis_mci.py spi-probe --transport spi --n 4 --read-bit 0
```

失败时，该命令会报告需要检查的内容，并且刻意不提供"模块有应答"作为安慰，因为在 SPIMCI 上这不构成任何信息。

### 6.3 读取模块

```
python cmis_mci.py bringup  --transport spi --n 4 --read-bit 0
python cmis_mci.py identify --transport spi --n 4 --read-bit 0
python cmis_mci.py read --transport spi --page 01h --byte 251 --n 4 --read-bit 0
```

请注意，最后一条命令中的页读取不需要写入页选择。页信息随事务头一起传输。

## 7 分析器带来了什么

使用 CMIS SPIMCI 分析器解码的 `CSn`、`CLK`、`IOTI` 和 `IITO` 采集会显示 4 + N + M 帧结构、
确认应答字节以及事务所寻址的寄存器。

除此之外，它还会报告规范实际定义的唯一错误条件，而通用解码器从结构上无法表示这一条件。

**ABORT。** 正常的 STOP 在预期时间落在 8 位边界上。不规则的 STOP，即落在非 8 位边界上或早于预期，
会终止事务，并且"任何未完整接收的字节都必须被接收方丢弃或忽略"。标准的 SPI 解码器会静默丢弃被片选撤销
所打断的字：没有帧，没有标志，也没有标记。这种情况恰恰就是 SPIMCI 的 ABORT 条件。

分析器还会显示 `N`，而不是将其隐藏。它可以被显式设置，可以以持续时间加速率的方式给出，也可以通过从字节 4 开始
向后扫描 `IITO` 上第一个 00h 或 FFh 来自动检测，并附带置信度指示，因为全零的数据字节可能造成混淆。

> **CMIS SPIMCI 分析器正在开发中，尚未发布。** 本节描述的是它产生的解码结果，而不是读者今天就能购买的产品。

### 8.2 结果

**观察结果，2026 年 8 月 15 日。** 在未连接任何模块的总线上发出的 SPIMCI 读取完成了，返回了有效的确认应答，
并返回 `00 00` 作为数据。这就是第 1 节所依据的观察结果，它是编码方式的特性，而不是任何特定模块的特性。

**观察结果，2026 年 9 月 2 日，情况比上面更糟。** 同样的探测在一块已存在、已上电且接线正确、
但未运行 SPIMCI 固件的电路板上运行，因此它返回的每个字节都是 `00h`。该命令没有报告模块不存在，
而是报告了一个正常的模块：

```
N        : 2 flow control bytes, transaction is 4 + 2 + M
R/Wn     : 0 means READ on this module
00h:222  : checksum 0x00 matches the stored byte

PASS     : the module is present and self consistent.
```

校验和之所以一致，是因为比较的两边都是零：94 字节的 `00h` 之和为 `00h`，而同一静默总线报告的存储校验和也是 `00h`。
第 6.2 节用于拒绝静默总线的检查本身被这种静默击败了，因此工具已被更正为：要求 Page 00h 包含不止一个不同的值，
校验和一致才算数。针对同一硬件，它现在报告：

```
FAIL     : no combination of N and R/Wn produced a valid Page 00h checksum.
           Either the module is absent, or CSn, CLK, IOTI or IITO are
           miswired. On SPIMCI a silent bus still returns a perfect ACK.
```

这正是本笔记自己的论点应验在了本笔记身上：一次看似成功的启动调试可能什么也没有读到。
实现附录 B.3 的主机也必须防范同样的情况。

**离线。** 本笔记所驱动的寄存器访问层与 AN0008 中自检的是同一个，针对模拟模块 8 项全部通过。
第八项正是本节所新增的：全零的 Page 00h 必须被拒绝，而不是被当作一致的校验和。

**在硬件上，针对模块。** 尚无。修订版 1.0 中待完成的事项：针对 SPIMCI 模块进行 `N` 扫描、极性判定、标识读取和
Page 00h 校验和验证。第 8.2 节确认的是失效模式及其防护措施，而不是成功路径。

## 9 故障排除

Table: 故障排除

| 现象 | 可能原因及处理方法 |
|---|---|
| 每个事务都成功，所有数据都是零 | 典型的伪造确认应答。模块不存在、未上电或未启用。只有同时要求 Page 00h 包含不止一个不同的值，校验和才能区分这种情况，因为 94 个零与值为零的存储校验和是一致的 |
| `spi-probe` 找不到有效组合 | 在怀疑 `N` 之前，先检查 `CSn`、`CLK`、`IOTI` 和 `IITO` 的接线。静默的总线仍然会给出确认应答 |
| 流控字节既不是 00h 也不是 FFh | `N` 错误，因此读到的字节是数据或控制字节，而不是确认应答 |
| 数据偏移了一个或多个字节 | `N` 偏差了相应的字节数。请重新运行扫描，而不是手动调整 |
| 读取能返回数据，写入似乎被忽略 | R/Wn 极性反了。尝试另一个 `--read-bit` |
| 事务在字中间被截断 | 不规则的 STOP，即 ABORT 条件。检查是否有其他器件在驱动 `CSn` |
| 适配器报告传输长度不足 | 传输长度与负载长度不一致。这是主机端的错误，而不是总线故障 |
