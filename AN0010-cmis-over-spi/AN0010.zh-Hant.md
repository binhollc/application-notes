## 1 簡介

您接好一個 SPIMCI 模組，發出一次讀取，它成功了。交易完成，確認回應存在，資料也傳回了。

但模組並沒有上電。

SPIMCI 將 ACK 編碼為 **00h**（B.3.7.1.2），因此全零是一個有效的確認回應，後面接著全零資料。
Binho 在實驗台上正好重現了這種情況：讀取完成，看到了確認回應，資料為 `00 00`。
一次完成的 SPIMCI 交易本身絕不能作為模組存在的證據。

本筆記以一種靜默無法偽造的方式啟動除錯 SPIMCI 鏈路，並順帶解決 SPIMCI 給主機帶來的第二個問題。

### 1.1 範圍

讀完本文件後，手邊有硬體的讀者將能夠確定其模組實作的流量控制位元組數與 R/Wn 極性、讀取其識別資訊，
並驗證其 Page 00h 檢查碼，而且在此過程中不會接受任何可能由不存在的模組產生的中間結果。

本文件涵蓋 SPI 管理介面，即 CMIS 附錄 B.3，它是規範性內容，於修訂版 5.3 引入。
AN0008 介紹暫存器模型，是本文件的前提。共同封裝光學系統設計不在本文範圍內。

## 3 SPIMCI 是什麼，以及為什麼值得理解它

SPIMCI 於 CMIS 5.3 引入，由共同封裝光學推動；修訂歷史中寫有「SPI-based SPIMCI in support of CPO」。
字串 `SPI` 在 CMIS 5.2 中從未出現。

它也是對未來任何繫結都至關重要的先例。它的加入完全沒有觸及暫存器存取層或 Common Data Block，
而且在加入的同時修正了定址方式。I2CMCI 只攜帶頁內位元組位址，因此需要 00h:126 與 00h:127 的頁選擇暫存器；
而 SPIMCI 交易攜帶完整的記憶庫、頁與位元組三維位址，具有隱含的頁切換，並且最多可傳輸 2048 位元組。

這對主機的實際意義是：**沒有需要寫入的頁選擇暫存器，也沒有可能出錯的跨交易位址狀態。**

Table: 規格固定的參數

| 參數 | 值 | 出處 |
|---|---|---|
| 字組大小 | 8 位元，最高有效位元在前 | B.3.7.2.3 |
| 取樣邊緣 | CLK 上升緣 | B.3.7.1 |
| 晶片選擇極性 | 低電位有效 | B.3.3 |
| 最大傳輸量 | 2048 位元組 | B.3.7.1 |

> **附註**：規格規定了取樣邊緣，但從未說明 CLK 的閒置電位，因此「SPIMCI 是 SPI 模式 0」是一種推論，
> 而不是引文。此工具程式預設使用模式 0，並允許選擇模式。

## 4 交易結構

每個 SPIMCI 交易都是 **4 + N + M** 位元組，分為三個階段。

Table: 交易控制階段，4 位元組，僅從發起端到目標裝置

| 位元 | 欄位 | 說明 |
|---|---|---|
| 0 | Command Type，R/Wn | 請見第 5.2 節 |
| 1:4 | Bank Index | 4 位元。規格指出這「不允許大於 15 的任意記憶庫索引值」 |
| 5:15 | EncodedSize | 11 位元。傳輸位元組數 = EncodedSize + 1，最大 2048 |
| 16:23 | Page Index | 8 位元 |
| 24:31 | Byte Index | 8 位元，起始位址。此後依序遞增 |

在整個控制階段，`IITO` 均未定義。

**流量控制階段，N 位元組，N 至少為 2。** 發起端傳送零值的虛擬位元組，目標裝置會忽略這些位元組。
目標裝置在該階段的**最後一個**位元組中，透過 `IITO` 傳回 **ACK = 00h** 或 **NACK = FFh**。

**資料傳輸階段，M = EncodedSize + 1 位元組。** 讀取時，資料在 `IITO` 上，`IOTI` 上傳送 00h。
寫入時，資料在 `IOTI` 上，`IITO` 未定義。

## 5 兩個未知數，以及如何確定它們

### 5.1 N 不在線路上傳輸，而且存在自舉漏洞

`N` 由 `00h:213` 位元 6-0 的 `MciFlowControlDuration` 與 `00h:213` 位元 7 的
`MciFlowControlDurationEncoding` 推導得出：

Table: 流量控制位元組數

| 編碼位元 | 推導方式 |
|---|---|
| 0，靜態 | N = 2 + 通告值 |
| 1，與速率相關 | N = max(2, ceil(duration x SpiSpeedInMHz / 8))，速率取自 `00h:27.3-0` 的 `MciSpeedConfiguration` |

B.3.7.1.2 要求雙方以完全相同的方式推導 `N`。但在已知 `N` 之前無法讀取 `00h:213`，而規格沒有指定安全的自舉值。
被動的匯流排觀察者同樣無法得知它。

解決方法是掃描 `N`，讓模組自身的檢查碼來判斷哪個值是正確的，這正是 `spi-probe` 所做的事。

### 5.2 R/Wn 極性自相矛盾

Table: CMIS 5.3 中的 R/Wn 極性

| 出處 | 規定 |
|---|---|
| B.3.7.1.1 | 「此位元為 1 時，表示請求讀取」 |
| B.3.8.1 至 B.3.8.5，圖 B-14 至 B-17 | 0 表示讀取 |

兩者都在同一份文件中。有一個值得了解的判定依據：B.3.8.5 將 **TEST** 定義為從位元組位址 0 進行的一位元組讀取，
而且**全部 32 個控制位元皆為零**，只有當 0 表示讀取時，這才是自洽的。此工具程式預設遵循圖示，
可依要求使用任一極性，在未指定時會探測兩種極性。

## 6 流程

### 6.1 離線確認工具

```
python cmis_mci.py selfcheck
```

### 6.2 確定 N 與極性

```
python cmis_mci.py spi-probe --transport spi
```

此命令針對每種極性將 `N` 從 2 掃描到 16，而且**僅**在 Page 00h 檢查碼驗證通過時才接受某個組合：
即 94 位元組的模組特定內容與模組自己寫入的一個位元組相符。一次完成的交易、一個確認回應，
甚至看似合理的資料，都可能由未上電的電路板產生。

> **注意**：未上電的電路板也可能產生相符的檢查碼，而且只有一種方式，恰好是實務中會出現的那種方式。
> 靜默的 SPI 匯流排對每個位元組都傳回 `00h`。九十四個 `00h` 位元組之和為 `00h`，而同一匯流排回報的儲存檢查碼也是 `00h`，
> 因此兩者一致。所以，只有當檢查碼驗證通過**而且** Page 00h 包含不只一個相異值時，掃描才會接受某個組合。
> 第 8.2 節記錄了加入此條件之前命令的回報內容。

若這些值已知，請直接傳入並略過掃描：

```
python cmis_mci.py spi-probe --transport spi --n 4 --read-bit 0
```

失敗時，此命令會回報需要檢查的內容，並刻意不提供「模組有回應」作為安慰，因為在 SPIMCI 上這不構成任何資訊。

### 6.3 讀取模組

```
python cmis_mci.py bringup  --transport spi --n 4 --read-bit 0
python cmis_mci.py identify --transport spi --n 4 --read-bit 0
python cmis_mci.py read --transport spi --page 01h --byte 251 --n 4 --read-bit 0
```

請注意，最後一個命令中的頁讀取不需要寫入頁選擇。頁資訊隨交易標頭一起傳輸。

## 7 分析器帶來了什麼

以 CMIS SPIMCI 分析器解碼的 `CSn`、`CLK`、`IOTI` 與 `IITO` 擷取會顯示 4 + N + M 訊框結構、
確認回應位元組，以及交易所定址的暫存器。

除此之外，它還會回報規格實際定義的唯一錯誤條件，而通用解碼器在結構上無法表示此條件。

**ABORT。** 正常的 STOP 在預期時間落在 8 位元邊界上。不規則的 STOP，即落在非 8 位元邊界上或早於預期，
會終止交易，而且「任何未完整接收的位元組都必須被接收端丟棄或忽略」。標準的 SPI 解碼器會靜默丟棄被晶片選擇解除
所中斷的字組：沒有訊框、沒有旗標，也沒有標記。這種情況正是 SPIMCI 的 ABORT 條件。

分析器也會顯示 `N`，而不是將其隱藏。它可以被明確設定，可以以持續時間加速率的方式給定，也可以從位元組 4 開始
向後掃描 `IITO` 上第一個 00h 或 FFh 來自動偵測，並附帶信心指標，因為全零的資料位元組可能造成混淆。

> **CMIS SPIMCI 分析器正在開發中，尚未發布。** 本節描述的是它產生的解碼結果，而不是讀者今天就能購買的產品。

### 8.2 結果

**觀察結果，2026 年 8 月 15 日。** 在未連接任何模組的匯流排上發出的 SPIMCI 讀取完成了，傳回了有效的確認回應，
並傳回 `00 00` 作為資料。這就是第 1 節所依據的觀察結果，它是編碼方式的特性，而不是任何特定模組的特性。

**觀察結果，2026 年 9 月 2 日，情況比上面更糟。** 同樣的探測在一塊已存在、已上電且接線正確、
但未執行 SPIMCI 韌體的電路板上執行，因此它傳回的每個位元組都是 `00h`。此命令沒有回報模組不存在，
而是回報了一個正常的模組：

```
N        : 2 flow control bytes, transaction is 4 + 2 + M
R/Wn     : 0 means READ on this module
00h:222  : checksum 0x00 matches the stored byte

PASS     : the module is present and self consistent.
```

檢查碼之所以一致，是因為比較的兩邊都是零：94 位元組的 `00h` 之和為 `00h`，而同一靜默匯流排回報的儲存檢查碼也是 `00h`。
第 6.2 節用來拒絕靜默匯流排的檢查本身被這種靜默擊敗了，因此工具程式已更正為：要求 Page 00h 包含不只一個相異值，
檢查碼一致才算數。針對同一硬體，它現在回報：

```
FAIL     : no combination of N and R/Wn produced a valid Page 00h checksum.
           Either the module is absent, or CSn, CLK, IOTI or IITO are
           miswired. On SPIMCI a silent bus still returns a perfect ACK.
```

這正是本筆記自己的論點應驗在本筆記身上：一次看似成功的啟動除錯可能什麼也沒有讀到。
實作附錄 B.3 的主機也必須防範同樣的情況。

**離線。** 本筆記所驅動的暫存器存取層與 AN0008 中自我檢查的是同一個，針對模擬模組 8 項全部通過。
第八項正是本節所新增的：全零的 Page 00h 必須被拒絕，而不是被當作一致的檢查碼。

**在硬體上，針對模組。** 尚無。修訂版 1.0 中待完成的事項：針對 SPIMCI 模組進行 `N` 掃描、極性判定、識別資訊讀取與
Page 00h 檢查碼驗證。第 8.2 節確認的是失效模式及其防護措施，而不是成功路徑。

## 9 疑難排解

Table: 疑難排解

| 症狀 | 可能原因與處理方式 |
|---|---|
| 每個交易都成功，所有資料都是零 | 典型的偽造確認回應。模組不存在、未上電或未啟用。只有同時要求 Page 00h 包含不只一個相異值，檢查碼才能區分這種情況，因為 94 個零與值為零的儲存檢查碼是一致的 |
| `spi-probe` 找不到有效組合 | 在懷疑 `N` 之前，先檢查 `CSn`、`CLK`、`IOTI` 與 `IITO` 的接線。靜默的匯流排仍然會給出確認回應 |
| 流量控制位元組既不是 00h 也不是 FFh | `N` 錯誤，因此讀到的位元組是資料或控制位元組，而不是確認回應 |
| 資料偏移了一個或多個位元組 | `N` 偏差了相應的位元組數。請重新執行掃描，而不是手動調整 |
| 讀取能傳回資料，寫入似乎被忽略 | R/Wn 極性相反。嘗試另一個 `--read-bit` |
| 交易在字組中間被截斷 | 不規則的 STOP，即 ABORT 條件。檢查是否有其他裝置在驅動 `CSn` |
| 轉接器回報傳輸長度不足 | 傳輸長度與酬載長度不一致。這是主機端的錯誤，而不是匯流排故障 |

| SPIMCI | SPI Management Communication Interface（SPI 管理通訊介面） |
