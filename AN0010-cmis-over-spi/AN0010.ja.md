## 1 はじめに

SPIMCI モジュールを配線し、読み出しを発行すると、うまく動作します。トランザクションは完了し、アクノリッジがあり、
データも返ってきます。

しかし、モジュールには電源が入っていません。

SPIMCI は ACK を **00h** としてエンコードする（B.3.7.1.2）ため、すべてゼロは有効なアクノリッジとそれに続くゼロのデータになります。
Binho はベンチでまさにこれを再現しました。読み出しは完了し、アクノリッジが確認され、データは `00 00` でした。
完了した SPIMCI トランザクションは、それ自体では決してモジュールが存在する証拠にはなりません。

本ノートでは、無応答では偽装できない方法で SPIMCI リンクを立ち上げ、その過程で SPIMCI がホストに課す 2 つ目の問題も解決します。

### 1.1 適用範囲

本書を読み終えると、ハードウェアを手元に持つ読者は、モジュールが実装しているフロー制御のバイト数と R/Wn の極性を確定し、
識別情報を読み出し、Page 00h のチェックサムを検証できるようになります。その間、存在しないモジュールでも生成され得るような
途中結果は一切受け入れません。

本書は、CMIS 付録 B.3 の SPI 管理インタフェースを対象とします。これは規範的なもので、リビジョン 5.3 で導入されました。
AN0008 はレジスタモデルを扱っており、前提となる資料です。コパッケージドオプティクスのシステム設計は対象外です。

Table: アダプタとモジュール間の接続

## 3 SPIMCI とは何か、そしてなぜ理解する価値があるのか

SPIMCI はコパッケージドオプティクスを契機として CMIS 5.3 で導入されました。改訂履歴には「SPI-based SPIMCI in support of CPO」と
記載されています。CMIS 5.2 には `SPI` という文字列はどこにも現れません。

これは、今後のあらゆるバインディングにとって重要な前例でもあります。SPIMCI は、レジスタアクセス層にも Common Data Block にも
まったく手を加えずに追加され、その際にアドレス指定も改善しました。I2CMCI はページ内のバイトアドレスしか運ばないため、
00h:126 と 00h:127 のページ選択レジスタを必要としますが、SPIMCI のトランザクションはバンク、ページ、バイトからなる完全な
3 次元アドレスを運び、暗黙のページ切り替えを行い、最大 2048 バイトを転送します。

ホストにとっての実際的な帰結は、**書き込むべきページ選択レジスタがなく、誤る可能性のあるトランザクションをまたぐアドレス状態もない**
ということです。

Table: 仕様で固定されているパラメータ

| パラメータ | 値 | 出典 |
|---|---|---|
| ワードサイズ | 8 ビット、MSB ファースト | B.3.7.2.3 |
| サンプリングエッジ | CLK の立ち上がりエッジ | B.3.7.1 |
| チップセレクトの極性 | アクティブロー | B.3.3 |
| 最大転送量 | 2048 バイト | B.3.7.1 |

> **注記**：仕様はサンプリングエッジを規定していますが、CLK のアイドルレベルについてはどこにも述べていません。そのため、
> 「SPIMCI は SPI モード 0 である」というのは引用ではなく推論です。ユーティリティはデフォルトでモード 0 を使用し、
> モードを選択可能にしています。

## 4 トランザクションの構造

すべての SPIMCI トランザクションは **4 + N + M** バイトで、3 つのフェーズから構成されます。

Table: トランザクション制御フェーズ、4 バイト、イニシエータからターゲットへのみ

| ビット | フィールド | 注記 |
|---|---|---|
| 0 | Command Type、R/Wn | セクション 5.2 を参照 |
| 1:4 | Bank Index | 4 ビット。仕様は、これが「15 を超える任意のバンクインデックス値を許容しない」と注記しています |
| 5:15 | EncodedSize | 11 ビット。転送バイト数 = EncodedSize + 1、最大 2048 |
| 16:23 | Page Index | 8 ビット |
| 24:31 | Byte Index | 8 ビット、開始アドレス。以降は連続 |

制御フェーズの間、`IITO` は全体を通して未定義です。

**フロー制御フェーズ、N バイト、N は 2 以上。** イニシエータはゼロ値のダミーバイトを送信し、ターゲットはそれを無視します。
ターゲットは、このフェーズの**最後の**バイトで、`IITO` 上に **ACK = 00h** または **NACK = FFh** を返します。

**データ転送フェーズ、M = EncodedSize + 1 バイト。** 読み出しでは、データは `IITO` 上にあり、`IOTI` には 00h が送信されます。
書き込みでは、データは `IOTI` 上にあり、`IITO` は未定義です。

## 5 2 つの未知数とその解決方法

### 5.1 N はワイヤ上になく、ブートストラップの穴がある

`N` は、`00h:213` のビット 6-0 にある `MciFlowControlDuration` と、`00h:213` のビット 7 にある
`MciFlowControlDurationEncoding` から導出されます。

Table: フロー制御のバイト数

| エンコードビット | 導出方法 |
|---|---|
| 0、静的 | N = 2 + アドバタイズされた値 |
| 1、速度依存 | N = max(2, ceil(duration x SpiSpeedInMHz / 8))、速度は `00h:27.3-0` の `MciSpeedConfiguration` から |

B.3.7.1.2 は、両側が `N` をまったく同じ方法で導出することを要求しています。しかし、`00h:213` は `N` がわかるまで読み出せず、
仕様は安全なブートストラップ値を示していません。パッシブなバスオブザーバにも、それを知る方法はありません。

解決策は、`N` をスイープし、どの値が正しいかをモジュール自身のチェックサムに判断させることであり、これが `spi-probe` の処理内容です。

### 5.2 R/Wn の極性が自己矛盾している

Table: CMIS 5.3 における R/Wn の極性

| 出典 | 記述 |
|---|---|
| B.3.7.1.1 | 「このビットが 1 のとき、読み出しが要求されている」 |
| B.3.8.1 から B.3.8.5、図 B-14 から B-17 | 読み出しは 0 |

どちらも同じ資料の中にあります。知っておく価値のある決め手があります。B.3.8.5 は **TEST** を、バイトアドレス 0 からの
1 バイト読み出しで、**32 個の制御ビットがすべてゼロ**のものとして定義しています。これは 0 が読み出しを意味する場合にのみ
自己整合します。ユーティリティはデフォルトで図に従い、要求に応じてどちらの極性も使用でき、指定がない場合は両方を探索します。

## 6 手順

### 6.1 オフラインでツールを確認する

```
python cmis_mci.py selfcheck
```

### 6.2 N と極性を確定する

```
python cmis_mci.py spi-probe --transport spi
```

このコマンドは、各極性について `N` を 2 から 16 までスイープし、Page 00h のチェックサムが検証された場合に**のみ**組み合わせを
受け入れます。すなわち、94 バイトのモジュール固有の内容が、モジュール自身が書き込んだバイトと一致する場合です。完了した
トランザクション、アクノリッジ、さらにはもっともらしく見えるデータでさえ、すべて電源の入っていないボードで生成され得ます。

> **注意**：一致するチェックサムも、電源の入っていないボードで生成され得ます。その方法はちょうど 1 つで、しかも実際に起こるのが
> その方法です。無応答の SPI バスはすべてのバイトに対して `00h` を返します。94 バイトの `00h` の合計は `00h` であり、
> 同じバスが格納済みチェックサムとして報告するのも `00h` であるため、両者は一致します。そのためスイープは、チェックサムが
> 検証され、**かつ** Page 00h に 2 種類以上の異なる値が含まれている場合にのみ組み合わせを受け入れます。セクション 8.2 には、
> この条件を追加する前にコマンドが報告した内容を記録しています。

値がすでにわかっている場合は、それを渡してスイープを省略します。

```
python cmis_mci.py spi-probe --transport spi --n 4 --read-bit 0
```

失敗した場合、コマンドは確認すべき事項を報告し、意図的に「モジュールは応答した」という慰めを示しません。
SPIMCI ではそれは何の情報にもならないからです。

### 6.3 モジュールを読み出す

```
python cmis_mci.py bringup  --transport spi --n 4 --read-bit 0
python cmis_mci.py identify --transport spi --n 4 --read-bit 0
python cmis_mci.py read --transport spi --page 01h --byte 251 --n 4 --read-bit 0
```

最後のコマンドのページ読み出しでは、ページ選択の書き込みが不要である点に注意してください。ページはトランザクションヘッダに
含まれて送られます。

## 7 アナライザがもたらすもの

CMIS SPIMCI アナライザでデコードした `CSn`、`CLK`、`IOTI`、`IITO` のキャプチャには、4 + N + M のフレーミング、
アクノリッジバイト、およびトランザクションがアドレス指定したレジスタが表示されます。

さらに、仕様が実際に定義している唯一のエラー条件を報告します。これは汎用デコーダでは構造上表現できないものです。

**ABORT。** 通常の STOP は、予定された時点で 8 ビット境界に位置します。8 ビット境界以外、または予定より早い不規則な STOP は
トランザクションを終了させ、「不完全に受信されたバイトは、受信側で破棄または無視されなければならない」とされています。
標準の SPI デコーダは、チップセレクトのデアサートによって中断されたワードを暗黙に破棄します。フレームもフラグもマーカーも
ありません。このケースこそが SPIMCI の ABORT 条件です。

アナライザは `N` を隠すのではなく表示します。`N` は明示的に設定することも、持続時間と速度で指定することも、`IITO` 上で
バイト 4 から前方へ最初の 00h または FFh を探索して自動検出することもでき、その際には信頼度インジケータが表示されます。
すべてゼロのデータバイトが紛れ込む可能性があるためです。

> **CMIS SPIMCI アナライザは開発中であり、まだリリースされていません。** このセクションでは、アナライザが生成するデコードを
> 説明しており、読者が現時点で購入できる製品を説明しているわけではありません。

### 8.2 結果

**観測、2026 年 8 月 15 日。** モジュールを接続していないバスに対して発行した SPIMCI 読み出しは完了し、有効なアクノリッジを返し、
データとして `00 00` を返しました。これがセクション 1 の根拠となる観測であり、特定のモジュールではなくエンコードの性質です。

**観測、2026 年 9 月 2 日。上記よりも悪い結果です。** 同じプローブを、存在し、電源が入り、正しく配線されているものの、
SPIMCI ファームウェアを実行していないボードに対して実行したため、返されたバイトはすべて `00h` でした。コマンドは
モジュールが存在しないとは報告しませんでした。正常なモジュールであると報告したのです。

```
N        : 2 flow control bytes, transaction is 4 + 2 + M
R/Wn     : 0 means READ on this module
00h:222  : checksum 0x00 matches the stored byte

PASS     : the module is present and self consistent.
```

チェックサムが一致したのは、比較の両側がゼロだったからです。94 バイトの `00h` の合計は `00h` であり、同じ無応答のバスが
格納済みチェックサムとして報告したのも `00h` でした。セクション 6.2 が無応答のバスを除外するために頼っていたチェック自体が
その無応答によって破られたため、ユーティリティは、チェックサムの一致を有効とみなす前に Page 00h に 2 種類以上の異なる値が
含まれていることを要求するよう修正されました。同じハードウェアに対して、現在は次のように報告します。

```
FAIL     : no combination of N and R/Wn produced a valid Page 00h checksum.
           Either the module is absent, or CSn, CLK, IOTI or IITO are
           miswired. On SPIMCI a silent bus still returns a perfect ACK.
```

これは本ノート自身の主張が本ノートに当てはまったものです。成功したように見える立ち上げが、実は何も読んでいないことがあるのです。
付録 B.3 を実装するホストも、同じケースに備えなければなりません。

**オフライン。** 本ノートが駆動するレジスタアクセス層は AN0008 がセルフチェックするものと同じで、シミュレーションモジュールに対して
8 項目中 8 項目に合格しています。8 番目のケースは、このセクションで追加したものです。すべてゼロの Page 00h は、一致した
チェックサムとして読むのではなく、拒否しなければなりません。

**ハードウェア上、モジュールに対して。** まだありません。リビジョン 1.0 で未完了の事項は、SPIMCI モジュールに対する
`N` のスイープ、極性の判定、識別情報の読み出し、および Page 00h のチェックサムです。セクション 8.2 で確立したのは
故障モードとそれに対するガードであり、成功経路ではありません。

## 9 トラブルシューティング

Table: トラブルシューティング

| 症状 | 考えられる原因と対処 |
|---|---|
| すべてのトランザクションが成功し、データがすべてゼロ | 典型的な偽のアクノリッジです。モジュールが存在しないか、電源が入っていないか、設定されていません。94 個のゼロは値ゼロの格納済みチェックサムと一致するため、Page 00h に 2 種類以上の異なる値が含まれていることも要求した場合にのみ、チェックサムでこれを区別できます |
| `spi-probe` で有効な組み合わせが見つからない | `N` を疑う前に、`CSn`、`CLK`、`IOTI`、`IITO` の配線を確認してください。無応答のバスでもアクノリッジは返ります |
| フロー制御バイトが 00h でも FFh でもない | `N` が誤っているため、読んでいるバイトはアクノリッジではなくデータまたは制御バイトです |
| データが 1 バイト以上ずれている | `N` がその分だけずれています。手作業で調整せず、スイープを再実行してください |
| 読み出しではデータが返るが、書き込みが無視されるように見える | R/Wn の極性が反転しています。もう一方の `--read-bit` を試してください |
| トランザクションがワードの途中で切れる | 不規則な STOP、すなわち ABORT 条件です。`CSn` を他に駆動しているものがないか確認してください |
| アダプタが転送不足を報告する | 転送長とペイロード長が一致していません。これはバスの障害ではなく、ホスト側のバグです |
