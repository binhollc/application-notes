## 1 簡介

I2C 目標裝置可在確認（ACK）其位址後將 SCL 保持為低電位，以爭取回應前的時間。控制器必須等到 SCL
被釋放。I2C 規範稱此為時脈延展（clock stretching），SMBus 允許最長 35 ms（tTIMEOUT）。SMBus 與
MCTP 裝置經常使用此機制：正在擷取數值的管理控制器會保持時脈，直到數值就緒為止。

Supernova 的 I3C 連接埠可以在與 I3C 裝置相同的匯流排上定址傳統 I2C 目標裝置。然而，其 I3C 引擎
在目標裝置將 SCL 保持為低電位時仍會持續產生時脈，因此會延展時脈的目標裝置會遺失位元，傳輸會傳回
錯誤資料或無確認（NACK）。主機轉接器韌體 4.6.0 與 pyCosmicSDK 1.6.0 新增了一種模式，可為 I3C
連接埠上的傳統 I2C 傳輸修正此問題。

## 2 系統概觀

此模式關閉時，I3C 連接埠上的 `legacy_i2c_read` 與 `legacy_i2c_write` 由 I3C 引擎執行，SCL 依其
自身的時序驅動。此模式開啟時，主機轉接器的韌體以軟體產生這些傳輸的時脈，並在每個釋放 SCL 的階段
之後檢查 SCL。當目標裝置將 SCL 保持為低電位時，韌體會等待。

有四項事實決定了此模式的使用方式：

- **這是一種模式，而非個別傳輸的選項。** `enable_i2c_clock_stretching(frequency_hz)` 會為之後的
  每一筆傳統 I2C 傳輸開啟此模式；`disable_i2c_clock_stretching()` 則將其關閉。`initialize` 與
  `configure` 也會將其關閉。
- **它排除 I3C 傳輸。** 開啟期間，SDR、HDR 與 CCC 呼叫、`init_bus` 與 `reset_bus` 會引發
  `I3cError`，狀態為 `FW_I3C_I2C_CLOCK_STRETCHING_ACTIVE`。與 I3C 裝置通訊前請先將其關閉。
- **它強制執行 SMBus 逾時。** 超過 35 ms 的延展會以 `FW_BUS_TIMEOUT` 結束傳輸，並釋放匯流排。
- **速率由軟體時脈設定。** 此呼叫接受 10 kHz 至 1 MHz，並傳回其計算出的速率：100 kHz 為 97975 Hz，
  400 kHz 為 391644 Hz，與線路上的實際值相差 1 % 以內。高於 400 kHz 時，傳回的速率與線路上的實際值
  最多相差 7 %，600 kHz 的要求實際以 615 kHz 執行（第 9.2 節）。此時脈上限約為 750 kHz，因此
  800 kHz 與 1 MHz 的要求都以該速率執行。

### 3.3 匯流排注意事項

I3C 連接埠在 SCL 上沒有上拉電阻。I2C 匯流排的兩條線都需要上拉電阻。在我們的測試台上，上拉電阻
來自一台 Binho Pulsar 的 I2C 連接埠，設定為 1 kOhm 並保持閒置；在兩條線各接一顆 1 kOhm 至
2.2 kOhm 的電阻至匯流排電壓，也能達到相同效果。SCL 上沒有上拉電阻時，回報的速率會大幅下降，因為
韌體會等待每一個上升緣。

> **注意：** I3C HV 連接埠的電壓由 `set_voltage` 選擇：1200 mV 至 3300 mV。在連接無法承受 3.3 V
> 的目標裝置之前，請先將其設定為目標裝置的 I/O 電壓。

> **注意：** 匯流排上只能有一個控制器。若由第二台主機轉接器提供上拉電阻，請勿從該轉接器發起傳輸。

### 3.4 參考目標裝置

為了量測此模式，我們需要一個延展時間可設定的目標裝置。資產壓縮檔中的 `stretch_target_pic18q20.c`
可將 PIC18F16Q20 Curiosity Nano 變成這樣的裝置。其 I2C 周邊在每次位址匹配後，會將 SCL 保持一段可
程式化的時間，這正是忙碌中的 SMBus 裝置的行為。

Table: 參考目標裝置協定，位址 0x2A

| 傳輸 | 效果 |
|---|---|
| 寫入 `0xF0`、低位元組、高位元組 | 在之後每次位址匹配後延展該微秒數；0 表示關閉延展 |
| 讀取 | 每個位元組皆傳回 `0xA5` |
| 任何其他寫入 | 接受並捨棄 |

SCL 與 SDA 位於 RB6 與 RB5。請以 MPLAB XC8 建置，並以 MPLAB X 或 Curiosity Nano 的拖放式燒錄器

## 5 時脈延展模式

### 5.1 使用方式

單獨列出的呼叫：

```python
import pycosmicsdk as p

dev = p.Device.open(model=p.DeviceModel.SUPERNOVA)
i3c = dev.i3c()
i3c.set_voltage(voltage_mv=3300)
i3c.bring_up(
    push_pull_rate=p.I3cPushPullRate.PUSH_PULL_1_MHZ_DC_40,
    open_drain_rate=p.I3cOpenDrainRate.OPEN_DRAIN_100_KHZ,
    i2c_open_drain_rate=p.I2cOpenDrainRate.STANDARD_MODE,
)
print(i3c.enable_i2c_clock_stretching(100_000))
# I2cClockStretching(enabled=True, frequency_hz=97975)
data = i3c.legacy_i2c_read(0x2A, 16)
i3c.disable_i2c_clock_stretching()
```

暫存器讀取，也就是 SMBus Read Byte 或 Read Word 模式，會將暫存器以 `subaddress` 傳入：
`i3c.legacy_i2c_read(0x0B, 2, subaddress=bytes([0x09]))`。

### 5.2 狀態碼

Table: 此模式特有的狀態碼

| 狀態 | 引發者 | 意義 |
|---|---|---|
| `FW_UNSUPPORTED_COMMAND` | enable、disable | 韌體 4.5.1 或更早版本 |
| `FW_INVALID_PARAMETER` | enable | 速率超出 10 kHz 至 1 MHz |
| `FW_INTERFACE_NOT_INITIALIZED` | enable、disable | I3C 控制器尚未啟動 |
| `FW_I3C_I2C_CLOCK_STRETCHING_ACTIVE` | SDR、HDR、CCC、`init_bus`、`reset_bus` | 此模式已開啟；請先將其關閉 |
| `FW_BUS_TIMEOUT` | 傳統讀取或寫入 | 目標裝置保持 SCL 超過 35 ms |

### 5.3 SMBus 逾時

在韌體驗證期間，將參考目標裝置設定為延展 40 ms，100 次讀取傳回 50 次 `FW_BUS_TIMEOUT` 與 50 次
`FW_I3C_NACK_ADDRESS`，最長為 46 ms，且主機轉接器保持可回應狀態。位址 NACK 來自目標裝置：它在仍
計數其 40 ms 期間錯過了下一個位址。

## 6 程序

1. 依第 3.2 節連接目標裝置與上拉電阻。為目標裝置供電。

2. 從目標裝置讀取。第一行顯示韌體與實際生效的速率：

```
$ python smbus_stretch.py read 0x2A 16
FW-4.6.1  I3C port 3300 mV  stretching on, SCL 97975 Hz
read  0x2A: a5 a5 a5 a5 a5 a5 a5 a5 a5 a5 a5 a5 a5 a5 a5 a5
```

3. 寫入目標裝置：

```
$ python smbus_stretch.py write 0x2A 0x01 0x02 0x03
FW-4.6.1  I3C port 3300 mV  stretching on, SCL 97975 Hz
write 0x2A: 01 02 03
```

4. 使用參考目標裝置掃描延展時間。對每個延展時間，腳本設定目標裝置的延展、讀取 16 位元組 100 次，
   並檢查每一個位元組：

```
$ python smbus_stretch.py sweep
FW-4.6.1  I3C port 3300 mV  stretching on, SCL 97975 Hz
  stretch  reads   ok  median ms  result
      0 us    100  100       6.02  all bytes correct
     50 us    100  100       6.02  all bytes correct
    500 us    100  100       7.20  all bytes correct
   2000 us    100  100       8.13  all bytes correct
  10000 us    100  100      18.01  all bytes correct
  30000 us    100  100      38.99  all bytes correct
```

5. 以 400 kHz 重複：

```
$ python smbus_stretch.py --khz 400 sweep
FW-4.6.1  I3C port 3300 mV  stretching on, SCL 391644 Hz
  stretch  reads   ok  median ms  result
      0 us    100  100       5.10  all bytes correct
     50 us    100  100       5.04  all bytes correct
    500 us    100  100       6.11  all bytes correct

  10000 us    100  100      16.90  all bytes correct
```

   每次讀取的中位時間隨延展時間增加，增加量約等於延展時間：主機轉接器每次都有等待。腳本在結束前
   會將目標裝置的延展設回 0。

## 7 SMBus 至 I3C Basic 偵測流程

從 SMBus 轉換至 I3C Basic 的 NVMe-MI 裝置共用同一對接腳，因此主機必須在變更匯流排之前，先查明每個
裝置使用哪一種協定。主機遵循的流程定義於 PCI-SIG Engineering Change Notice 第 12 章
Architectural Out-of-Band Management。`smbus_stretch.py` 的 `handoff` 命令會在 Supernova I3C
連接埠上執行此流程。表 7 列出各步驟及其執行者。

Table: 偵測流程步驟

| 步驟 | 流程 | 執行者 |
|---|---|---|
| 1 | 在 SMBus 電壓下，向 7Eh 廣播帶 DISHJ 的 DISEC；ACK 表示存在 I3C Basic 裝置 | 腳本。只有 7Eh 標頭為開汲極；CCC 位元組與資料以 I3C 速率推挽傳送。NACK 會回報為 `FW_I3C_NACK_ADDRESS` |
| 2 | 在靜態位址與 61h（ARP Get UDID）進行 SMBus 裝置探索 | 腳本，開啟時脈延展模式。腳本會檢查 PEC |
| 3 | 找到僅支援 SMBus 的裝置：重設 SMBus 介面並維持 SMBus 模式 | 腳本：`hold_scl_low` 將 SCL 保持低電位 T2wrst（`--t2wrst-us`）。具有 SMRST# 的裝置可改由 GPIO 重設 |
| 4 | 再次發送帶 DISHJ 的 DISEC，接著關閉 SMBus 上拉電阻並開啟 I3C Basic 上拉電阻 | DISEC 由腳本執行。主機轉接器的 SDA 上拉電阻在 SMBus 階段以 `set_sda_pull_up`（`--sda-pull-up`）設定，之後則跟隨 I3C 引擎。主機轉接器在 SCL 上沒有上拉電阻：外部上拉電阻需手動切換 |
| 5 | 等待 Tsmb2i3c，切換至 I3C Basic 電壓，廣播帶 ENHJ 的 ENEC | 腳本。`--t-smb2i3c-ms` 與 `--i3c-voltage-mv` 的值來自規範與裝置 |
| 6 | 裝置執行熱加入（Hot-Join） | 韌體：由韌體自行指派動態位址，腳本將其印出 |

時脈延展模式會拒絕所有 CCC（第 5.2 節），因此腳本只在步驟 2 開啟此模式，並在步驟 4 之前再次關閉。

若要在 Saleae 分析儀上檢視此流程，`capture_flow.py` 會透過 Logic 2 的自動化伺服器開始擷取，以 `--`
之後的引數執行 `handoff`，並以 Logic 2 的 I2C 分析器與 `flow_labels` 擴充功能儲存擷取結果，該擴充
功能會在專屬的列上標示每個步驟。`--step-delay-s` 會拉開各步驟之間的間隔，以便在時間軸上找到每個
步驟。

> **說明：** 只有僅 SMBus 的分支實際執行過，在第 9.1 節的測試台上以韌體 4.6.1 執行 6 次，6 次結果
> 完全相同，其中一次是在主機轉接器重設之後：步驟 1 為 NACK，步驟 2 在 0x2A 找到參考目標裝置且未
> 找到 ARP 裝置，要求 35000 us 時，SMBus 重設將 SCL 保持低電位 35000 至 35777 us。步驟 3 至 6
> 需要會對 7Eh 回應 ACK 並執行熱加入的裝置，ARP 與 PEC 路徑則需要支援 ARP 的裝置；測試台上兩者皆
> 沒有。PEC 常式僅以 CRC-8/SMBUS 的檢查值驗證過。

```
$ python smbus_stretch.py --khz 400 handoff --address 0x2A 0x2B --sda-pull-up ON --t2wrst-us 35000
FW-4.6.1  I3C port 3300 mV (SMBus voltage)
1. DISEC(DISHJ) to 7Eh: NACK, SMBus only
2. SMBus discovery, stretching on, SCL 391644 Hz
  static 0x2A: ACK
  static 0x2B: FW_I3C_NACK_ADDRESS
  ARP 0x61 Get UDID: FW_I3C_NACK_ADDRESS (no ARP-capable device)
   SMBus mode stays.
   SMBus reset: SCL held low 35059 us (asked 35000 us)
```

### 9.2 結果

第 6 節的掃描在兩種速率與六種延展時間下共讀取 1200 次，每次 16 位元組。共執行三次，第三次在主機
轉接器重設之後：3600 次正確，沒有錯誤。

以下為相同功能在韌體驗證期間、於預發行建置上取得的其他結果：

- 長時間測試，隨機進行 1 至 64 位元組的讀取與寫入，每 100 次傳輸在 0、50 us、500 us、2 ms 與
  10 ms 之間切換延展時間：在 100 kHz 與 400 kHz 下，每次執行約 3400 次經延展的傳輸中有 0 次錯誤
  讀取，包含一次在電源重啟後的執行。

韌體 4.6.1 上依要求值的 SCL 速率。高於 400 kHz 時，每個延展時間（50 us 至 30 ms）讀取 20 次，
每次 16 位元組：

Table: 依要求值的 SCL 速率

| 要求值 | 回報值 | 線路上的實際值 | tLOW / tHIGH | 經延展的讀取 |
|---|---|---|---|---|
| 100 kHz | 97975 Hz | 98.2 kHz | 5105 / 5075 ns | 1500 次中 1500 次 |
| 400 kHz | 391644 Hz | 395.3 kHz | 1600 / 935 ns | 1500 次中 1500 次 |
| 600 kHz | 583657 Hz | 615.4 kHz | 855 / 755 ns | 100 次中 100 次 |
| 800 kHz | 746268 Hz | 749.1 kHz | 750 / 585 ns | 100 次中 100 次 |
| 1 MHz | 746268 Hz | 749.1 kHz | 750 / 585 ns | 100 次中 100 次 |

線路上的實際值為每個速率約 9000 個 SCL 週期的中位數。每個速率的 tLOW 與 tHIGH 都高於 UM10204 對其
模式規定的最小值。高於 400 kHz 時，傳回的速率不會跟隨線路上的實際值：500 kHz 的要求回報
477707 Hz，實際以 467.3 kHz 執行；700 kHz 回報 652173 Hz，實際以 696.9 kHz 執行；600 kHz 則比
要求值高 2.6 %。若高於 400 kHz 的精確速率很重要，請量測線路。

參考目標裝置不延展時，高於 400 kHz 的讀取會在第二個位元組傳回 0xFF，每個速率 100 次中 0 次正確，
而每一次經延展的讀取都正確。兩種情況下主機轉接器的 SCL 相同；只有目標裝置本身的時脈延展關閉。我們
將其歸因於參考目標裝置的韌體在不延展時未能及時載入第二個位元組，而非主機轉接器。

SMBus 重設（`hold_scl_low`），每個點保持 5 次，預發行韌體 `FW-4.5.1-b11a067e`，SCL 低電位時間以
Acute 量測。跨越分析儀緩衝區邊界的保持，讀數約短 1.5 ms，已排除：

Table: SMBus 重設的 SCL 保持

| 要求值 | 線路上的量測值 | 主機轉接器回報值 | 保持後的讀取 |
|---|---|---|---|
| 1 ms | 999.7 至 1678 us | 1000 至 1677 us | 5 次中 5 次 |
| 10 ms | 9987 至 11006 us | 10000 至 10998 us | 5 次中 5 次 |
| 35 ms | 34996 至 35941 us | 35000 至 35937 us | 每種模式 5 次中 5 次，重設後亦同 |
| 100 ms | 100013 至 100114 us | 100000 us | 5 次中 5 次 |

保持時間最多可能長約 1 ms，相對於分析儀的時脈最多短 0.13 %，這是主機轉接器內部振盪器的容差；要求
T2wrst 時請預留此餘裕。0 us 與超過 1 s 會以 `FW_INVALID_PARAMETER` 拒絕，韌體 4.5.1 則回應
`FW_UNSUPPORTED_COMMAND`。

SDA 上拉電阻，以 Pulsar 的上拉電阻關閉時，每個 STOP 從 SCL 上升到 SDA 越過 1.6 V 的延遲量測：
`OFF` 為 7813 ns，`ON` 為 5975 ns，`AUTO` 為 5965 ns。三種設定下，不論是否開啟時脈延展模式，
讀取皆為 10 次中 10 次。

## 10 疑難排解

Table: 疑難排解

| 症狀 | 可能原因與處置 |
|---|---|
| 開啟時出現 `FW_UNSUPPORTED_COMMAND` | 韌體 4.5.1 或更早版本。請將 Supernova 更新至 4.6.0 或更新版本。 |
| 回報的速率遠低於要求值 | SCL 上沒有上拉電阻。請加上一個（第 3.3 節）。 |
| `FW_I3C_I2C_CLOCK_STRETCHING_ACTIVE` | 在此模式開啟時進行了 I3C 呼叫。請先呼叫 `disable_i2c_clock_stretching`。 |
| `FW_BUS_TIMEOUT` | 目標裝置保持 SCL 超過 35 ms。請檢查目標裝置；這是 SMBus 的 tTIMEOUT。 |
| 重新設定參考目標裝置後立即出現 `FW_I3C_NACK_ADDRESS` | 目標裝置會重新啟動其 I2C 周邊以套用新的延展時間。腳本會為此等待 10 ms。 |
| 此模式關閉時，從會延展時脈的目標裝置取得錯誤資料 | 預期行為：I3C 引擎不會等待。請開啟此模式。 |
| 高於 400 kHz 時開啟出現 `FW_INVALID_PARAMETER` | 韌體早於 4.6.0 的 1 MHz 上限。請更新 Supernova。 |
| 高於 400 kHz 時 `sweep` 出現 `FW_I3C_I2C_NACK_BYTE` | 參考目標裝置在不延展時錯過了重新設定的寫入：在我們的測試台上 24 次掃描中有 1 次。請再執行一次掃描。 |
| `capture_flow.py` 在 Saleae Logic Pro 上解碼出錯誤的位址與資料 | 數位臨界值為裝置預設值。3.3 V 匯流排請傳入 `--threshold 3.3`：在我們的 Logic Pro 8 上，同一次掃描中於 SCL 為高電位時看到的 SDA 邊緣從 732 個減少為 50 個，且全部都是 START 與 STOP。 |
| 匯流排上有 I3C Basic 裝置時 `handoff` 步驟 1 為 NACK | 該裝置在所設定的電壓下不處於 SMBus 模式，或未供電。請檢查 `--voltage-mv`。 |
