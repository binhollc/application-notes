## 1 Introduction

An I2C target may hold SCL low after it acknowledges its address, to gain time before it answers.
The controller must wait until SCL is released. The I2C specification calls this clock
stretching, and SMBus allows it for up to 35 ms (tTIMEOUT). SMBus and MCTP devices use it
routinely: a management controller that is fetching a value holds the clock until the value is
ready.

The Supernova's I3C port can address legacy I2C targets on the same bus as I3C devices. Its I3C
engine, however, keeps clocking while a target holds SCL low, so a stretching target misses bits
and the transfer returns wrong data or no acknowledge. Adapter firmware 4.6.0 and pyCosmicSDK
1.6.0 add a mode that fixes this for legacy I2C transfers on the I3C port.

### 1.1 Scope

This document covers:

- what the clock-stretching mode changes, and what it refuses while it is on
- the SCL rates it runs at and how close they come to the request
- a script that reads and writes a stretching target through the mode
- a reference target that stretches for a configurable time, and its firmware
- measured results against that target
- the SMBus to I3C Basic detection flow used for NVMe-MI, and which of its steps the adapter
  performs

It does not cover SMBus framing beyond the PEC check of an ARP Get UDID (block read and write,
quick command), MCTP or NVMe-MI messages, or the Supernova's separate I2C port.

## 2 System overview

With the mode off, `legacy_i2c_read` and `legacy_i2c_write` on the I3C port are carried out by the
I3C engine, which drives SCL on its own schedule. With the mode on, the adapter's firmware clocks
those transfers in software and checks SCL after every phase it releases. When a target holds SCL
low, the firmware waits.

Four facts shape how the mode is used:

- **It is a mode, not a per-transfer option.** `enable_i2c_clock_stretching(frequency_hz)` turns it
  on for every later legacy I2C transfer; `disable_i2c_clock_stretching()` turns it off.
  `initialize` and `configure` also turn it off.
- **It excludes I3C traffic.** While it is on, SDR, HDR and CCC calls, `init_bus` and `reset_bus`
  raise `I3cError` with status `FW_I3C_I2C_CLOCK_STRETCHING_ACTIVE`. Turn it off before talking to
  an I3C device.
- **It enforces the SMBus timeout.** A stretch longer than 35 ms ends the transfer with
  `FW_BUS_TIMEOUT`, and the bus is released.
- **The rate is never above the request.** The call returns the rate in effect. It is 10 kHz to
  1 MHz; at 100 kHz the adapter runs at 97975 Hz, at 400 kHz at 391644 Hz. The software clock
  tops out at 746268 Hz, so 800 kHz and 1 MHz requests both run there.

### 3.3 Bus considerations

The I3C port has no pull-up on SCL. An I2C bus needs one on both lines. On our bench it came from a
Binho Pulsar's I2C port set to 1 kOhm and left idle; a pair of 1 kOhm to 2.2 kOhm resistors to the
bus voltage does the same job. Without a pull-up on SCL the reported rate drops sharply, because
the firmware waits for every rising edge.

> **Caution:** the I3C HV port selects its voltage from `set_voltage`: 1200 mV to 3300 mV. Set it to
> the target's I/O voltage before connecting a target that is not 3.3 V tolerant.

> **Caution:** only one controller on the bus. If a second adapter supplies the pull-up, do not
> start transfers from it.

### 3.4 The reference target

To measure the mode we needed a target whose stretch we could set. `stretch_target_pic18q20.c`, in
the assets archive, turns a PIC18F16Q20 Curiosity Nano into one. Its I2C peripheral holds SCL after
every address match for a programmable time, which is how a busy SMBus device behaves.

Table: Reference target protocol, address 0x2A

| Transfer | Effect |
|---|---|
| write `0xF0`, low byte, high byte | stretch that many microseconds after every later address match; 0 turns stretching off |
| read | returns `0xA5` for every byte |
| any other write | accepted and discarded |

SCL and SDA are on RB6 and RB5. Build it with MPLAB XC8 and program it with MPLAB X or the Curiosity
Nano's drag-and-drop programmer.

## 5 The clock-stretching mode

### 5.1 Using it

The calls in isolation:

```python
import pycosmicsdk as p

dev = p.Device.open(model=p.DeviceModel.SUPERNOVA)
i3c = dev.i3c()
i3c.set_voltage(voltage_mv=3300)
i3c.bring_up(
    push_pull_rate=p.I3cPushPullRate.PUSH_PULL_1_MHZ_DC_40,
    open_drain_rate=p.I3cOpenDrainRate.OPEN_DRAIN_100_KHZ,
    i2c_open_drain_rate=p.I2cOpenDrainRate.STANDARD_MODE,
)
print(i3c.enable_i2c_clock_stretching(100_000))
# I2cClockStretching(enabled=True, frequency_hz=97975)
data = i3c.legacy_i2c_read(0x2A, 16)
i3c.disable_i2c_clock_stretching()
```

A register read, the SMBus Read Byte or Read Word pattern, passes the register as `subaddress`:
`i3c.legacy_i2c_read(0x0B, 2, subaddress=bytes([0x09]))`.

### 5.2 Status codes

Table: Status codes specific to the mode

| Status | Raised by | Meaning |
|---|---|---|
| `FW_UNSUPPORTED_COMMAND` | enable, disable | firmware 4.5.1 or earlier |
| `FW_INVALID_PARAMETER` | enable | rate outside 10 kHz to 1 MHz |
| `FW_INTERFACE_NOT_INITIALIZED` | enable, disable | the I3C controller was not brought up |
| `FW_I3C_I2C_CLOCK_STRETCHING_ACTIVE` | SDR, HDR, CCC, `init_bus`, `reset_bus` | the mode is on; turn it off first |
| `FW_BUS_TIMEOUT` | legacy read or write | the target held SCL longer than 35 ms |

### 5.3 The SMBus timeout

During firmware validation, with the reference target set to stretch 40 ms, 100 reads returned 50
`FW_BUS_TIMEOUT` and 50 `FW_I3C_NACK_ADDRESS`, the longest in 46 ms, and the adapter stayed
responsive. The address NACKs come from the target, which misses the next address while it is
still counting out its 40 ms.

## 6 Procedure

1. Connect the target and the pull-ups as in section 3.2. Power the target.

2. Read from the target. The first line shows the firmware and the rate in effect:

```
$ python smbus_stretch.py read 0x2A 16
FW-4.5.1-def51e1c  I3C port 3300 mV  stretching on, SCL 97975 Hz
read  0x2A: a5 a5 a5 a5 a5 a5 a5 a5 a5 a5 a5 a5 a5 a5 a5 a5
```

3. Write to it:

```
$ python smbus_stretch.py write 0x2A 0x01 0x02 0x03
FW-4.5.1-def51e1c  I3C port 3300 mV  stretching on, SCL 97975 Hz
write 0x2A: 01 02 03
```

4. With the reference target, sweep the stretch. For each duration the script sets the target's
   stretch, reads 16 bytes 100 times, and checks every byte:

```
$ python smbus_stretch.py sweep
FW-4.5.1-def51e1c  I3C port 3300 mV  stretching on, SCL 97975 Hz
  stretch  reads   ok  median ms  result
      0 us    100  100       6.19  all bytes correct
     50 us    100  100       6.79  all bytes correct
    500 us    100  100       7.13  all bytes correct
   2000 us    100  100       9.26  all bytes correct
  10000 us    100  100      17.89  all bytes correct
  30000 us    100  100      39.05  all bytes correct
```

5. Repeat at 400 kHz:

```
$ python smbus_stretch.py --khz 400 sweep
FW-4.5.1-def51e1c  I3C port 3300 mV  stretching on, SCL 391644 Hz
  stretch  reads   ok  median ms  result
      0 us    100  100       5.08  all bytes correct
     50 us    100  100       5.04  all bytes correct
    500 us    100  100       6.35  all bytes correct
   2000 us    100  100       8.46  all bytes correct
  10000 us    100  100      16.78  all bytes correct
  30000 us    100  100      37.92  all bytes correct
```

   The median time per read grows with the stretch, and by about the stretch: the adapter waited
   each time. The script sets the target's stretch back to 0 before it exits.

## 7 The SMBus to I3C Basic detection flow

NVMe-MI devices that move from SMBus to I3C Basic share one pair of pins, so the host has to find
out which protocol each device speaks before it changes the bus. The flow the host follows is
defined in the PCI-SIG Engineering Change Notice, Chapter 12, Architectural Out-of-Band
Management. The `handoff` command of `smbus_stretch.py` runs it on the Supernova I3C port.
Table 7 lists the steps and who performs each.

Table: Detection flow steps

| Step | Flow | Performed by |
|---|---|---|
| 1 | Broadcast DISEC with DISHJ to 7Eh at the SMBus voltage; ACK means an I3C Basic device is present | script. Only the 7Eh header is open-drain; the CCC byte and data are push-pull at the I3C rate. A NACK is reported as `FW_I3C_NACK_ADDRESS` |
| 2 | SMBus device discovery at static addresses and at 61h (ARP Get UDID) | script, with the clock-stretching mode on. The script checks the PEC |
| 3 | An SMBus-only device was found: reset the SMBus interface and stay in SMBus mode | script: `hold_scl_low` holds SCL low for T2wrst (`--t2wrst-us`). A device with SMRST# can be reset from a GPIO instead |
| 4 | DISEC with DISHJ again, then SMBus pull-ups off and I3C Basic pull-ups on | script for DISEC. The adapter's SDA pull-up is set with `set_sda_pull_up` (`--sda-pull-up`) for the SMBus phase and follows the I3C engine after it. SCL has no pull-up on the adapter: the external one is switched by hand |
| 5 | Wait Tsmb2i3c, move to the I3C Basic voltage, broadcast ENEC with ENHJ | script. `--t-smb2i3c-ms` and `--i3c-voltage-mv` come from the specification and the device |
| 6 | The device Hot-Joins | firmware: it assigns the dynamic address itself and the script prints it |

The clock-stretching mode refuses every CCC (section 5.2), so the script turns it on for step 2
only and off again before step 4.

> **Note:** only the SMBus-only branch has been run, 5 of 5 identical, on the bench of section 9.1:
> step 1 NACKed, step 2 found the reference target at 0x2A and no ARP device, and the SMBus reset
> held SCL low for 35000 to 35922 us when asked for 35000 us. Steps 3 to 6 need a
> device that ACKs 7Eh and Hot-Joins, and the ARP and PEC path needs an ARP-capable device;
> neither was on the bench. The PEC routine is checked against the CRC-8/SMBUS check value only.

```
$ python smbus_stretch.py --khz 400 handoff --address 0x2A 0x2B --sda-pull-up ON --t2wrst-us 35000
FW-4.5.1-b11a067e  I3C port 3300 mV (SMBus voltage)
1. DISEC(DISHJ) to 7Eh: NACK, SMBus only
2. SMBus discovery, stretching on, SCL 391644 Hz
  static 0x2A: ACK
  static 0x2B: FW_I3C_NACK_ADDRESS
  ARP 0x61 Get UDID: FW_I3C_NACK_ADDRESS (no ARP-capable device)
   SMBus mode stays.
   SMBus reset: SCL held low 35874 us (asked 35000 us)
```

### 9.2 Results

The sweeps of section 6 read 1200 times, 16 bytes each, across both rates and six stretch
durations: 1200 correct, no errors.

Further results from the firmware validation of the same feature, on earlier builds:

- Soak with random 1 to 64 byte reads and writes, the stretch changing every 100 transfers among 0,
  50 us, 500 us, 2 ms and 10 ms: 0 bad reads in about 3400 stretched transfers per run at 100 kHz
  and 400 kHz, including a run after a power cycle.
- Measured on the wire at a 1 kOhm pull-up: a 100 kHz request runs at 97.9 kHz and a 400 kHz
  request at 391.4 kHz, with tLOW and tHIGH at or above the UM10204 minimums.

Above 400 kHz, with the target stretching 50 us to 30 ms, 20 reads of 16 bytes per point:

Table: Rates above 400 kHz

| Request | Reported | On the wire | tLOW / tHIGH | Stretched reads |
|---|---|---|---|---|
| 400 kHz | 391644 Hz | 394.5 kHz | 1625 / 910 ns | 100 of 100 |
| 600 kHz | 581395 Hz | 561.8 kHz | 965 / 820 ns | 100 of 100 |
| 800 kHz | 746268 Hz | 754.7 kHz | 815 / 515 ns | 100 of 100, and 100 of 100 after each of 3 resets |
| 1 MHz | 746268 Hz | not measured | not measured | 100 of 100 |

On-the-wire values are medians over about 23000 SCL periods on an Acute logic analyzer. At
800 kHz both phases stay above the UM10204 Fast-mode Plus minimums of 500 ns and 260 ns. At
600 kHz the reported rate is 3.5 % above the wire.

With the reference target not stretching, reads above 400 kHz return 0xFF in the second byte,
0 of 100 at each rate, while every stretched read is correct. The adapter's SCL is the same in
both cases; only the target's own clock stretching is off. We attribute it to the reference
target's firmware not loading the second byte in time without stretching, not to the adapter.

SMBus reset (`hold_scl_low`), 5 holds per point, firmware `FW-4.5.1-b11a067e`, SCL low time on the
Acute. Holds that span one of the analyzer's buffer boundaries read about 1.5 ms short and are
left out:

Table: SCL hold for the SMBus reset

| Requested | Measured on the wire | Reported by the adapter | Reads after the hold |
|---|---|---|---|
| 1 ms | 999.7 to 1678 us | 1000 to 1677 us | 5 of 5 |
| 10 ms | 9987 to 11006 us | 10000 to 10998 us | 5 of 5 |
| 35 ms | 34996 to 35941 us | 35000 to 35937 us | 5 of 5 per mode, and after a reset |
| 100 ms | 100013 to 100114 us | 100000 us | 5 of 5 |

A hold can run up to about 1 ms long, and up to 0.13 % short against the analyzer's clock, which
is the tolerance of the adapter's internal oscillator; ask for T2wrst with that margin. 0 us and
more than 1 s are refused with `FW_INVALID_PARAMETER`, and firmware 4.5.1 answers
`FW_UNSUPPORTED_COMMAND`.

The SDA pull-up, measured as the delay from SCL rising to SDA crossing 1.6 V at each STOP with
the Pulsar's pull-up off: 7813 ns with `OFF`, 5975 ns with `ON` and 5965 ns with `AUTO`.
Reads were 10 of 10 in all three settings, with and without the clock-stretching mode.

These are what we measured on one bench, not a specification.

> **Note:** on the pre-release builds, the first `enable_i2c_clock_stretching` after an `init_bus`
> that failed (no I3C device answered) may report about half the rate at 100 kHz, or time out at
> 10 kHz. The rate on the wire is correct. This is being fixed for the release; the procedure
> above does not call `init_bus`.

## 10 Troubleshooting

Table: Troubleshooting

| Symptom | Probable cause and action |
|---|---|
| `FW_UNSUPPORTED_COMMAND` on enable | Firmware 4.5.1 or earlier. Update the Supernova to 4.6.0 or later. |
| Reported rate far below the request | No pull-up on SCL. Add one (section 3.3). |
| `FW_I3C_I2C_CLOCK_STRETCHING_ACTIVE` | An I3C call was made with the mode on. Call `disable_i2c_clock_stretching` first. |
| `FW_BUS_TIMEOUT` | The target held SCL longer than 35 ms. Check the target; this is SMBus tTIMEOUT. |
| `FW_I3C_NACK_ADDRESS` right after reconfiguring the reference target | The target restarts its I2C peripheral to apply a new stretch. The script waits 10 ms for this. |
| Wrong data from a stretching target with the mode off | Expected: the I3C engine does not wait. Turn the mode on. |
| `FW_INVALID_PARAMETER` on enable above 400 kHz | Firmware before 4.6.0's 1 MHz limit. Update the Supernova. |
| `handoff` step 1 NACK with an I3C Basic device on the bus | The device is not in SMBus mode at the voltage set, or not powered. Check `--voltage-mv`. |
