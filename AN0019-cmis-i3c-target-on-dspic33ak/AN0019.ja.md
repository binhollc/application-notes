## 1 はじめに

CMIS モジュールは 256 バイトのウィンドウを公開します。これは Lower Memory と Upper Memory の 128 バイトのページ 1 つから成り、
ページは `00h:127` のページバイトで選択されます。I2C では、ホストはバイトアドレスを書き込み、その後リピーテッド START で
読み出します。CMIS 向けに定義が進められている I3C 管理インタフェースはこのアクセスパターンを維持しているため、
I3C ターゲットペリフェラル上に構築したモジュールは、同じ転送の中でわずか数ビット時間前に到着したバイトアドレスに対する
読み出しに応答しなければなりません。

ペリフェラルが各バイトを到着時にファームウェアへ渡すのであれば、これは容易です。しかし dsPIC33AK256MPS306 の
I3C ペリフェラルはコマンドとレスポンスに基づいて動作します。受信した転送はレスポンスとして 1 回だけ報告され、読み出しには
送信コマンドで応答しますが、その送信コマンドはリードヘッダが到着した時点ですでに有効でなければなりません。
本アプリケーションノートは、この 2 つをかみ合わせる方法について説明します。

### 1.1 対象範囲

- dsPIC33AK 上の CMIS レジスタモデル：ページング、セクション 8.2.15 の非サポートページの置き換え、
  Appendix B.1.2 の 128 バイトセグメント内でのラップ、および Flags Summary バイト `00h:4` を運ぶ IBI。
- 2.5 MHz プッシュプルでの、書き込み + Sr + 読み出し（コンバインド）と、書き込み、STOP、読み出し（スプリット）への応答。
- ダイナミックアドレス割り当て（DAA）、RSTDAA、および Direct GET CCC。
- 本ノートのすべてのチェックを Supernova から実行するホストスクリプト。

対象外：CDB、ファームウェアのダウンロード、HDR モード、および CMIS 制御レジスタのモジュール側での意味。
レジスタイメージは、ページ選択とホストが書き込むバイトを除いて静的です。

## 2 システム概要

Supernova は I3C コントローラであり、バス上の唯一のコントローラです。dsPIC33AK はターゲットで、スタティックアドレスは
CMIS モジュールアドレスである `0x50` です。コントローラは ENTDAA でダイナミックアドレスを割り当て（ベンチでは `0x08` を
割り当てます）、その後 SDR で読み書きします。

ファームウェアの形を決める唯一の事実は、コンバインドリードのバイトアドレスがいつ見えるようになるかです。I3C 割り込みを
無効にし、100 MHz タイマを基準にペリフェラルをポーリングし、ロジックアナライザと時刻を合わせて測定した結果は次のとおりです。

Table: 2.5 MHz プッシュプルでのコンバインドリード、START からの時間

| イベント | 時間 |
|---|---|
| バイトアドレスの T ビット | 22.3 µs |
| 受信 FIFO 内のバイトアドレス | 23.8 µs |
| リピーテッド START | 24.1 µs |
| リードヘッダの ACK スロット | ~27.4 µs |
| 書き込みのレスポンス割り込み | ACK スロットの後 |

書き込みのレスポンス割り込みからアームした送信コマンドは常に遅すぎ、ターゲットは読み出しを NACK します。バイトアドレス
自体は ACK スロットの 3.6 µs 前に得られ、コマンドのアームには 1.15 から 1.26 µs かかります。そこでファームウェアは
受信 DMA からアームします。受信したワードを RAM へ転送するチャネルが、I3C 割り込みより高い優先度でワードごとに割り込みを
発生させ、その割り込みが最初のバイトから送信コマンドをアームします。

その他のことはすべて、このペリフェラルとその MCC Melody ドライバの 3 つの特性から導かれます。

- 1 つの送信コマンドは 1 回の読み出しに応答します。ファームウェアはバイトアドレスからセグメントの終わりまでの
  128 バイトのランをアームし、コントローラが読み出しを早めに終了します。
- 送信バッファは 8 ワード（32 バイト）を保持します。ランの残りはメインループから供給されます。32 バイトの送信に
  かかる時間（約 115 µs）より長くメインループを離れさせる処理があると、読み出しは 32 バイトで打ち切られます。
- 受信を再アームすると受信 FIFO がリセットされ、アーム済みの送信コマンドも破棄されます。受信は読み出しの後にのみ
  再アームします。

## 5 ターゲットファームウェアの設計

### 5.1 レジスタモデル

Lower Memory と Upper Memory のページ `00h` は、CMIS 5.3 Appendix C の例のイメージに基づいています。`00h:127` の
ページ選択は `00h` と `01h` を受け付け、それ以外の値は `00h` に置き換えられます（セクション 8.2.15）。各セグメントは
連続して 2 回格納され、さらに 1 から 3 バイトずらしたコピーも格納されるため、任意のバイトアドレスからの 128 バイトの
ランは 1 つのアラインされたバッファとなり、セグメント内の B.1.2 ラップにはコードが不要です。

### 5.2 識別情報

Table: コントローラから見える識別情報

| 項目 | 値 |
|---|---|
| スタティックアドレス | `0x50` |
| PID | `02 36 43 4D 49 53`（MIPI メーカー `0x11B`、部品 `"CMIS"`） |
| BCR | `0x17`：IBI 対応、IBI は 1 バイトを運ぶ、最大データ速度制限あり |
| DCR | `0x00` |

### 5.3 読み出しのアーム

1. 受信 DMA チャネルは受信した各ワードを `rxbuf` に転送します。その完了割り込みは有効で、優先度は 5 であり、
   優先度 4 の I3C 割り込みより高くなっています。
2. 書き込みの最初のワードで、DMA 割り込みは `rxbuf[0]` をバイトアドレスとして取得し、そのアドレスからのランの
   送信コマンドをアームします。
3. 書き込みのレスポンスが到着し、それがアドレスのみを運んでいた場合、コマンドはアームされたままとなり、受信は
   読み出しの完了後に再アームされます。
4. 書き込みがデータを運んでいた場合、拡張送信バッファをリセットしてコマンドを取り消し、受信を直ちに再アームします。
5. リードヘッダの時点でまだ何もアームされていない場合、ペリフェラルはリードリクエストを発生させます。ファームウェアは
   遅れてアームされたものをすべて破棄し、`I3C1_Target_ReceiveCancel()` で受信を再アームします。この場合、書き込みの
   レスポンスは決して来ないためです。

### 5.4 長い読み出しへの供給

送信バッファにはあらかじめ 8 ワードを充填しておきます。`I3C1_Target_TxRefill()` が残りをメインループから供給し、
その実行にかかる数命令の間は I3C 割り込みと DMA 割り込みをマスクします。ブリングアップ用ファームウェアの UART
ステータス行はデフォルトでオフです。9600 baud でのブロッキング `printf` が 1 秒あたり約 110 ms メインループを占有し、
128 バイトの読み出しを 32 バイトで打ち切っていたためです。

### 5.5 イベント

IBI が有効な間、IBI は 1 秒に 1 回、`00h:4` を必須のデータバイトとして運びます。ペリフェラルは I3C Basic の規定どおり
IBI が有効な状態でリセットから復帰し、そのイネーブルに書き込まれた 0 を保持しません。IBI を無効にするには DISEC を
使用します。

### 5.6 Melody ドライバへの変更

Table: `mcc/` 内のローカル変更（`binho:` でマーク）

| 変更 | 理由 |
|---|---|
| `BufferTransmit` が 8 ワードを事前充填し、`I3C1_Target_TxRefill()` が残りを供給 | 8 ワードを超えると DMA パスがワード 7 を 2 回書き込んで先へ進まず、コマンドが拒否されていたため |
| `I3C1_Target_ReceiveCancel()` | 書き込み + Sr + NACK されたリードヘッダの後、書き込みのレスポンスは来ない。ドライバは受信を処理中としてマークしたままにし、以降のすべての受信を拒否していた |
| 完了コールバックの前に `rxInProgress` をクリア | コールバックが受信を再アームできるようにするため |
| スタティックアドレス `0x50` | CMIS モジュールアドレス |

## 6 手順

**ステップ 1**：ファームウェアフォルダからターゲットをビルドし、書き込みます。

```
make flash
```

ビルドは MPLAB IPE の `Program Succeeded.` で終了します。

**ステップ 2**：表 4 のとおり、Supernova の I3C ポートを DIM に配線します。

**ステップ 3**：書き込み + Sr + 読み出しで 128 バイトを 60 回読み出します。

```
python cmis_target_check.py reads --length 128 --count 60
```

```
init bus: FW_I3C_BUS_INIT_NACK_RSTDAA
target DA 0x08, PID 02 36 43 4d 49 53
............................................................
reads 60/60  (combined, 128 B, IBI off)
```

`init bus` の行は、リセット後の最初の RSTDAA が NACK されたことを示します（セクション 8.3）。スクリプトは再度
初期化します。

**ステップ 4**：IBI を有効にして同じことを行います（読み出しの前に ENEC）。

```
python cmis_target_check.py reads --length 128 --count 300 --ibi
```

```
reads 299/300  (combined, 128 B, IBI on)
```

ドットの行の `F` はエラーが発生した読み出しを、`B` は誤ったデータを返した読み出しを示します。

**ステップ 5**：データ書き込みと読み出しの混在：各ラウンドで `7Fh=00h` と `7Eh=00h` を書き込み、その後 `7Fh`
（1 バイト）と `80h`（16 バイト）を読み出し、イメージと照合します。

```
python cmis_target_check.py mixed --count 60
```

```
rounds 60/60
```

**ステップ 6**：アドレスのリセットと再割り当て：

```
python cmis_target_check.py daa --cycles 10
```

```
0: RSTDAA SUCCESS, GETSTATUS at old DA FW_I3C_NACK_ADDRESS, read after ENTDAA ok
...
cycles 10/10
```

**ステップ 7**：識別情報と Direct GET CCC：

```
python cmis_target_check.py ccc --getstatus 100
```

```
GETBCR   SUCCESS                17
GETDCR   SUCCESS                00
GETPID   SUCCESS                02 36 43 4d 49 53
GETMXDS  SUCCESS                00 00 00 00 01
GETMRL   FW_I3C_NACK_ADDRESS    
GETMWL   SUCCESS                ff
GETSTATUS 100/100  {'SUCCESS': 100}
```

Direct GET は NACK された `7Eh` ヘッダで失敗することがあります（セクション 8.3）。ここでは GETMRL が失敗しました。
もう一度実行してください。

## 7 リファレンス

Table: `cmis_target_check.py` のコマンド

| コマンド | 動作 |
|---|---|
| `reads --length N --count N [--split] [--ibi]` | `00h`、`10h`、`7Ch`、`80h`、`A0h`、`FCh` を順に読み出し、イメージと比較します。`--split` を指定しない限りコンバインド。`--ibi` は先に ENEC を送り、指定しなければ DISEC を送ります |

### 8.3 ホストが想定すべき挙動

- **ターゲットのリセット後の最初の転送は NACK されます**。5 回のリセットのそれぞれの後、最初の `7Eh` ヘッダは NACK され、
  2 回目は ACK されました。DS70005539 のセクション 24.4.5 には、モジュールは SCL クロックを検出して初めてリセットから
  抜けると記載されています。1 回だけプローブして NACK を「I3C ターゲットなし」と判断するホストは、このモジュールを
  見落とします。プローブを再試行してください。
- **一部の Direct GET CCC は NACK された `7Eh` で失敗します**。あるセッションでは、Direct GET に続く `7Eh` ヘッダの
  約 7 回に 1 回が NACK されました（1200 回の GET で 173 回失敗し、173 回すべてがワイヤ上で `7E/W NACK` として
  確認できました）。別のセッションでは 500 回中 500 回が成功しました。プライベートリードには影響しませんでした。
  NACK で失敗した GET は再試行してください。
- **GETMRL は 255 を報告し、SETMRL は適用されません**。ファームウェアは 128 を設定しますが、ペリフェラルが自ら GETMRL に
  255 で応答します。SETMRL 16 の後も、32 バイトの読み出しは 32 バイトを返します。

### 8.4 アドレス割り当て前の I2C 読み出し

ENTDAA の前、ターゲットは `0x50` で I2C に応答します。Supernova の I2C ポート（3.3 V で 2.2 kOhm のプルアップを持つ
通常の I2C コントローラ）から、各実行の前にターゲットを書き込んだうえで、`00h`、`10h`、`7Ch`、`80h`、`A0h`、`FCh` で
3、4、16、128 バイトを読み出したところ、100 kHz と 400 kHz のどちらでも各 30/30 で、データはイメージと一致しました。
各転送を `7Eh` ヘッダで開始する I2C モードの I3C ポートからは、セッション 1 では 30 回中 8 回が正しく、セッション 3 では
リセット後の最初の読み出しが NACK され、2 回目は `00h:46-48` から `80 00 00` を返しました。

## 9 トラブルシューティング

Table: トラブルシューティング

| 症状 | 考えられる原因と対処 |
|---|---|
| すべてのコンバインドリードが `FW_I3C_NACK_ADDRESS` で失敗する | コマンドのアームが遅すぎます。DMA 割り込みの優先度が I3C 割り込みより高いこと、およびその中で時間のかかる処理が実行されていないことを確認してください |
| 128 バイトの読み出しが失敗し、アナライザに 308 個の SCL クロックが表示される | 読み出しが 32 バイトで打ち切られています。メインループが送信バッファに供給していません。ブロッキング `printf` などを取り除いてください |
| 読み出しの失敗後、リセットするまでターゲットが応答しなくなる | 受信が処理中としてマークされたままです。ファームウェアに `I3C1_Target_ReceiveCancel()` が必要です |
| 電源投入後の最初の初期化が `FW_I3C_BUS_INIT_NACK_RSTDAA` で失敗する | リセット後の最初の転送は NACK されます。再度初期化してください |
| MPLAB IPE が "Connection Failed" または `Transmission on endpoint 2 failed (err = -150)` を報告する | PKoB4 の USB を抜き差しする必要があります |
