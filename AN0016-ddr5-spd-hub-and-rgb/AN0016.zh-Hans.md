## 1 简介

DDR5 DIMM 提供一条独立于内存总线的两线边带（HSCL、HSDA）。在该总线上首先应答的是
SPD5118 Hub；它保存模块的 SPD 数据、报告温度，并把流量转发到模块本地总线上的其他器件，
例如 PMIC，以及在带灯光的模块上的 RGB 控制器。Hub 以 I2C 模式启动，可以切换到 I3C。

本笔记介绍如何在没有主板的情况下，从主机适配器读取 Hub 及上述器件。

### 1.1 范围

本文档涵盖：

- 识别 SPD5118 Hub、读取其温度传感器，以及读取 1 KB 的 SPD NVM
- 读取 PMIC 状态，仅读取
- 使用 SETAASA 将 Hub 切换到 I3C、以 SDR 读取，并使用 RSTDAA 返回 I2C
- 在本测试台上返回正确数据的 I3C 速率，以及未返回正确数据的那个速率
- 位于 Hub 后方的 Corsair RGB 控制器：使其退出固件更新模式、逐个 LED 设置颜色，以及启动硬件效果

本文档不涵盖：写入 SPD NVM、通过 I3C 写入 Hub 寄存器（第 5.3 节说明原因）、来自 Hub 的
带内中断（IBI）（已尝试，未收到）、PEC，以及在 Hub 处于 I3C 模式时访问 RGB 控制器（未尝试）。

## 2 系统概述

Table: 边带上看到的器件，Hub 处于 I2C 模式，100 kHz

| 地址 | 器件 | 应答方式 |
|---|---|---|
| `0x50` | SPD5118 Hub | 寄存器指针 + 读取；裸读取也应答 |
| `0x48` | PMIC | 寄存器指针 + 读取 |
| `0x18` | Corsair RGB 控制器 | **仅限寄存器指针 + 读取**；裸读取不被应答 |

该模块的 HSA 被配置为 0，这使 Hub 位于 `0x50`。Hub 把发往模块本地总线上器件的传输转发到
主机侧；JESD300-5 将这两个地址字段称为本地 ID（local ID）和主机 ID（host ID）。在 I2C 模式下，
这种转发不需要任何配置。PMIC 和 RGB 控制器都通过它访问。

以下两个事实决定了下文的全部内容：

- **裸读取扫描找不到 RGB 控制器。** 用一字节读取扫描 `0x08` 到 `0x77`，只返回 `0x48` 和
  `0x50`。先写入寄存器指针再读取，才能在 `0x18` 找到它。
- **在本测试台上，Hub 是一个不会被 ENTDAA 发现的 I3C 目标器件。** 收到 SETAASA 时，它将其
  静态地址作为动态地址；收到 RSTDAA 时返回 I2C。

## 5 寄存器与协议

### 5.1 I2C 模式下的 SPD5118 Hub

所有访问都是一个一字节寄存器指针，后跟一次读取。

Table: 使用的 Hub 寄存器

| 寄存器 | 本模块上的读数 | 含义 |
|---|---|---|
| MR0-1 | `51 18` | 器件类型，SPD5118 |
| MR2 | `0x14` | 器件版本 |
| MR5 | `0x03` | 能力：Hub 和温度传感器 |
| MR11 | `0x00` | I2C 传统模式：位 2:0 选择 NVM 页，位 3 选择 2 字节寻址 |
| MR12-13 | `FF 7F` | NVM 写保护，每个 64 字节块一位 |
| MR18 | I2C 下为 `0x00`，I3C 下为 `0x20` | 位 5 = I3C 模式 |
| MR49-50 | 两个字节 | 温度 |

**温度。** MR50 位 4:0 和 MR49 位 7:0 组成一个 13 位字段，其中位 1:0 未使用。其余 11 位为
二进制补码，每 LSB 为 0.25 °C：

```python
raw = (((mr50 & 0x1F) << 8) | mr49) >> 2
if raw & 0x400:
    raw -= 0x800
celsius = raw * 0.25
```

在测试台上，该模块读数为 27 到 29 °C。其限值寄存器读数为 55 °C（高）和 85 °C（临界）。

**NVM。** 1024 字节的 NVM 由八个 128 字节的页组成。在 1 字节寻址下，位 7 置位的指针寻址
NVM，位 6:0 为页内偏移，MR11 位 2:0 为页号。读取全部内容的方法：保存 MR11，依次把页 0 到 7
写入其中，每次从指针 `0x80` 读取 128 字节，然后写回保存的值。MR11 是唯一被写入的寄存器。
该模块的转储解码为字节 2 = `0x12`（DDR5）和字节 3 = `0x02`（UDIMM），且字节 0 到 509 上的
CRC-16（多项式 `0x1021`，初始值 0）与字节 510 和 511 中存储的值一致。

**PMIC。** 寄存器 R32 读数为 `0x80`（稳压器已使能），且未置位任何故障位。PMIC 仅被读取。

### 5.2 I3C 模式下的 SPD5118 Hub

1. 以 I3C 模式启动控制器。
2. 广播 SETAASA，器件表中包含 `0x50`。MR18 从 `0x00` 变为 `0x20`。
3. 使用寄存器指针以 SDR 读取：`sdr_read(0x50, n, subaddress=bytes([reg]))`。
4. 广播 RSTDAA。通过 I2C 读取时，MR18 再次为 `0x00`。

`init_bus()` 使用 ENTDAA 发现目标器件，在本测试台上未能启动 Hub。请使用 SETAASA。

Table: 1.1 V 下从 Hub 进行的 I3C SDR 读取，按推挽速率

| 推挽速率 | 结果 |
|---|---|
| 1 MHz | 20/20 |
| 5 MHz | 50/50（首次运行为 20/20） |
| 6.25 MHz | 50/50 |
| 7.5 MHz | 50/50 |
| 10 MHz | 50/50 |
| 12.5 MHz | 9/50 正确；其余 41 次在成功状态下返回了错误数据 |

12.5 MHz 下的失败并未被报告为错误：读取已完成，但数据错误。转接板布线在 1.1 V 下可能是
限制因素。**在较长的边带布线上请使用 4 MHz 或更低。** 已测量 1 MHz（20/20）以及 5 到 10 MHz；
两者之间的速率未测量。`ddr5_spd.py --i3c` 默认使用 1 MHz。

### 5.3 通过 I3C 写入寄存器

> **注意：** 在 I3C SDR 模式下对 Hub 的寄存器写入未按写入的值生效，随后总线挂起。写入为
> 26.5 °C 的温度限值回读为 48 °C；向 MR27 写入的 `0x01` 回读为 `0x10`。此后，每个 I3C 操作都
> 返回 `FW_I3C_ENGINE_BUSY`。重启 Supernova 无法清除该状态，对 LV 连接器重新上电也不行。只有
> 给模块重新上电才能清除。原因（Hub 的 I3C 写入格式或主机侧）尚未确定。在 I3C 模式下只进行
> 读取。如果需要写入，请在 I2C 模式下进行，或先写入一个无害的寄存器并通过回读确认。

### 5.4 Corsair RGB 控制器

以下寄存器映射和数据包格式来自 OpenRGB 的 Corsair DRAM 控制器（GPL-2.0）。本文档中的脚本
根据该描述重新实现；未复制任何 OpenRGB 代码。在 Hub 处于 I2C 模式时，通过 `0x18` 访问该控制器。

每次访问都是写入 `[register, value]`，或寄存器指针后跟一字节读取。**控制器空闲一段时间后的
第一次访问可能被拒绝一次；请重试。**

Table: 使用的 RGB 控制器寄存器

| 寄存器 | 访问 | 用途 |
|---|---|---|
| `0x0B`, `0x21` | 写入 `0x00` | 复位数据包缓冲区及其 CRC |
| `0x20` | 写入，每次访问一个字节 | 数据包缓冲区 |
| `0x42` | 读取 | 自复位以来加载的字节的 CRC-8 |
| `0x82` | 写入 | 应用：`0x01` 效果数据包，`0x02` 颜色缓冲区 |
| `0x30` | 读取 | 应用过程中位 3 置位 |
| `0x61` 然后 `0x21` | 写入 `0x00` | 选择器件信息块 |
| `0x40` | 读取，32 次 | 器件信息块 |
| `0x23` | 写入 `0x01` | 退出固件更新模式 |

CRC 为 CRC-8，多项式 `0x07`，初始值 0。应用之前请将其与 `0x42` 比较；不一致表示有字节丢失
或重复（重试写入可能导致这种情况），此时不得应用该数据包。

**器件信息块。** 字节 0-1 为 VID，小端序；字节 2-3 为 PID；字节 28 为协议版本。

**固件更新模式。** 两端的 LED 都亮红色，是 Corsair 文档中所述的固件更新（引导加载程序）
模式指示。在该状态下，模块报告 PID `0x0B00` 和协议 1，并接受效果数据包（CRC 一致），但 LED
不变化。向 `0x23` 写入一次 `0x01` 后，它变为 PID `0x0B01`、协议 4，出厂彩虹效果随之亮起
（图 1）。模块如何进入该模式尚未确定；它在上电后不久曾被探测过。

> **注意：** 切勿向寄存器 `0x23` 写入 `0x00`。

![退出固件更新模式后的模块：出厂彩虹效果。](figures/an0016-fig1-after-bootloader.png)

**颜色缓冲区。** 六个 `R, G, B, 0xFF` 条目，每个 LED 一个，共 24 字节，在复位后加载到
`0x20`，检查 CRC，并以 `0x82` = `0x02` 应用。由此可设置单一颜色和逐 LED 颜色（图 2）。该缓冲区
仅在静态模式下显示：在动画效果下，它会被接受（包括 CRC），但会被忽略。因此
`ddr5_rgb.py color` 会先发送静态效果（模式 `0x10`）。

![颜色缓冲区：六个 LED 全部为红色（左），每个 LED 一种颜色（右）。](figures/an0016-fig2-colour-buffer.png)

**效果数据包。** 20 字节，以 `0x82` = `0x01` 应用：

```
mode, speed, 0x01, direction, R1, G1, B1, brightness, R2, G2, B2, brightness, 0 x 8
```

Table: 效果模式

| 模式 | 代码 | 在本模块上观察到 |
|---|---|---|
| 彩虹波（rainbow wave） | `0x03` | 是 |
| 静态（static） | `0x10` | 已应用，但保持了之前的颜色；请改用颜色缓冲区 |
| 彩虹（rainbow） | `0x08` | 未观察到 |
| 脉冲（pulse） | `0x01` | 未观察到 |

## 6 操作步骤

### 6.1 上电与连接

通过转接板给模块供电。将电缆连接到 Supernova I3C LV 连接器。

### 6.2 识别 Hub 并读取其温度


```
python ddr5_spd.py --serial <serial>
```

测试台上的输出：

```
MR0-1 5118  (SPD5118 reads 5118)
MR2 revision 0x14  MR18 0x00  (bit 5 = I3C mode)
MR49-50 CC 01 = 28.75 C
```

### 6.3 保存 NVM（可选）

将 NVM 保存到您选择的文件中。请将该文件视为可识别该模块的信息：它包含模块的序列号。

```
python ddr5_spd.py --serial <serial> --nvm my_module_spd.bin
```

脚本会恢复 MR11，并报告 SPD CRC 是否一致：

```
MR0-1 5118  (SPD5118 reads 5118)
MR2 revision 0x14  MR18 0x00  (bit 5 = I3C mode)
MR49-50 CC 01 = 28.75 C
NVM: 1024 bytes to my_module_spd.bin, MR11 restored to 0x00
SPD byte 2 0x12 (0x12 = DDR5), byte 3 0x02, CRC 0-509 calc 0x45BF stored 0x45BF OK
```

### 6.4 以 I3C 模式读取 Hub（可选）

脚本使用 SETAASA 进入 I3C 模式，以 SDR 读取，然后使用 RSTDAA 将 Hub 返回 I2C：

```
python ddr5_spd.py --serial <serial> --i3c --i3c-mhz 1
```

在 I3C 读取期间 MR18 读数为 `0x20`，RSTDAA 之后为 `0x00`：

```
MR0-1 5118  (SPD5118 reads 5118)
MR2 revision 0x14  MR18 0x00  (bit 5 = I3C mode)
MR49-50 CC 01 = 28.75 C
I3C SDR: MR18 0x20  MR0-1 5118  temperature 29.00 C
after RSTDAA (I2C): MR18 0x00
```

在适配器固件 4.6.1 上，每次适配器复位后此操作可执行 11 次；参见第 9 节。

### 6.5 读取 RGB 控制器的器件信息


```
python ddr5_rgb.py --serial <serial> info
```

测试台上的输出，控制器处于正常模式：

```
VID 0x1B1C PID 0x0B01 protocol 4
```

### 6.6 退出固件更新模式

如果 PID 为 `0x0B00`（两端为红色），请退出固件更新模式。脚本仅在 PID 为 `0x0B00` 时才写入。

```
python ddr5_rgb.py --serial <serial> leave-bootloader
```

控制器处于固件更新模式时的输出：

```
before: PID 0x0B00 protocol 1
after:  PID 0x0B01 protocol 4
```

以及控制器已处于正常模式时的输出：

```
before: PID 0x0B01 protocol 4
not in firmware-update mode; nothing written
```

### 6.7 设置颜色或效果


```
python ddr5_rgb.py --serial <serial> color 255,0,0
python ddr5_rgb.py --serial <serial> color 255,0,0 255,80,0 255,220,0 0,255,0 0,0,255 160,0,255
python ddr5_rgb.py --serial <serial> effect wave 255,0,0 0,0,255 --speed 2
python ddr5_rgb.py --serial <serial> demo
```

这些命令成功时不输出任何内容；如果控制器的 CRC 不一致，则以错误退出。

演示序列见 `figures/an0016-video1-rgb-demo.mp4`（42 s），由该脚本所整合自的测试台脚本录制。

| `demo` | 红、绿、蓝、白，逐 LED 彩虹，追逐效果，然后彩虹波 |

两个脚本对每次访问最多重试三次（`ddr5_spd.py`）或五次（`ddr5_rgb.py`）。

## 9 故障排除

Table: 故障排除

| 现象 | 原因 | 处理 |
|---|---|---|
| 扫描找到 `0x48` 和 `0x50`，但 `0x18` 处没有器件 | RGB 控制器不应答裸读取 | 写入寄存器指针后读取，如 `ddr5_rgb.py info` 所做 |
| 对 `0x18` 的第一次访问被拒绝，下一次成功 | 控制器处于空闲状态 | 重试；脚本会自动重试 |
| 两端 LED 为红色，效果数据包被接受但没有任何变化 | 控制器处于固件更新模式，PID `0x0B00` | `ddr5_rgb.py leave-bootloader` |
| 之后控制器在未重新上电的情况下又回到固件更新模式 | 在广播 CCC 流量（RSTDAA/ENTDAA）和适配器复位之后出现；原因未查明 | 运行 `ddr5_rgb.py info`；如果 PID 为 `0x0B00`，再次执行 `leave-bootloader` |
| 对 Hub 的每次 I2C 读取都返回 `51 FF`，无论寄存器为何 | Hub 被之前的 SETAASA 留在 I3C 模式（MR18 位 5 置位） | 发送 RSTDAA，或给模块重新上电 |
| 多次 I3C 会话后 SETAASA 被拒绝：目标器件表已满（见下文） | 适配器固件 4.6.1 在 RSTDAA 之后的每次 SETAASA 都添加一个目标器件表条目；第 12 次失败（3/3 次运行） | 复位适配器（`reboot` 或重新插拔）；已在适配器固件中跟踪 |
| 颜色被接受（CRC 一致），但 LED 继续播放动画 | 控制器正在运行动画效果；颜色缓冲区仅在静态模式下显示 | `ddr5_rgb.py color` 会先选择静态模式；使用原始写入时，请先发送静态效果，再发送颜色 |
| `0x42` 处 CRC 不一致 | 加载时有字节丢失或重复 | 重新发送整个数据包；不要应用 |
| `init_bus()` 找不到 Hub | 在本测试台上 Hub 不会被 ENTDAA 发现 | 使用 `ccc.setaasa([0x50])` |
| 完全没有器件应答 | 1200 mV 或更高会选择 HV 连接器 | 请求 1100 mV |
| I3C 模式下数据错误但状态为成功 | 推挽速率相对于布线过高 | 4 MHz 或更低 |
| I3C 写入后每个 I3C 操作都返回 `FW_I3C_ENGINE_BUSY` | Hub 挂起（第 5.3 节） | 给模块重新上电；重启 Supernova 无法清除 |
| NVM 转储 CRC 不一致 | MR11 被更改，或转储过程中某次读取失败 | 重新运行；检查 MR11 位 3 为 0 |

目标器件表已满导致的拒绝报告为 `FW_NOT_ENOUGH_SPACE_IN_TARGET_DEVICES_TABLE`。

## 10 缩略语

Table: 缩略语

| 术语 | 含义 |

| PID, VID | 产品 ID，厂商 ID（Product ID, vendor ID） |
