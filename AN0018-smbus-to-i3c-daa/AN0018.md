## 1 Introduction

Some devices power up as SMBus targets at 3.3 V and can move to I3C at 1.8 V. The host decides
when: it first makes sure that every device left on the bus can follow, then lowers the bus
voltage and assigns dynamic addresses. A device that only speaks SMBus would not survive the
move, so the host stays in SMBus mode if it finds one.

The Supernova's I3C port speaks SMBus (legacy I2C) and I3C on the same two pins, and its voltage
is set from software. The whole sequence therefore runs from one port and one script.

### 1.1 Scope

This document covers:

- the five steps of the sequence and the pyCosmicSDK call behind each one
- the wiring, and where the bus pull-ups must go so that they follow the voltage change
- a script that runs the sequence, with SETDASA or ENTDAA as the address assignment
- measured results on a bench with a Supernova as the I3C device

It does not cover the SMBus to I3C Basic detection flow of the PCI-SIG out-of-band management
specification (Hot-Join, ARP, the SMBus reset), which AN0014 covers, or MCTP and NVMe-MI messages.

## 2 System overview

Table 3 lists the steps and the call that performs each.

Table: Steps of the sequence

| Step | Action | pyCosmicSDK call |
|---|---|---|
| 1 | Operate in SMBus mode at 3.3 V | `set_voltage(voltage_mv=3300)`, `bring_up(...)`, `ccc.rstdaa()` |
| 2 | Broadcast a 7Eh command. An ACK means at least one I3C device is on the bus | `ccc.disec_broadcast(I3cEvent.HJ)`; a NACK raises `I3cError` with `FW_I3C_NACK_ADDRESS` |
| 3 | Probe every SMBus address. A device that answers and is not a known I3C device is SMBus-only; if one remains, stay in SMBus mode | `legacy_i2c_read(address, 1)` for 08h to 77h |
| 4 | Move the bus and its pull-ups from 3.3 V to 1.8 V | `set_voltage(voltage_mv=1800)` |
| 5 | Assign dynamic addresses with SETDASA or ENTDAA, then read each device's PID | `ccc.setdasa(static=, dynamic=)` or `init_bus()`, then `ccc.getpid(address)` |

Three facts shape the sequence:

- **Step 2 is a CCC, not an SMBus transfer.** Only the 7Eh header is sent open-drain, so an
  SMBus-only device sees an address it does not own and ignores it. The CCC used is DISEC with
  DISHJ, which also keeps the I3C devices from Hot-Joining while the host is still in SMBus mode.
- **Step 3 needs a list of the I3C devices' static addresses.** An I3C device with a static
  address also answers an SMBus read at that address, so an answer alone does not prove a device
  is SMBus-only. The script takes the I3C devices' static addresses (`--i3c-static`) and treats
  any other answer as SMBus-only.
- **Step 4 moves the pull-ups only if they hang from the port voltage.** The Supernova's SDA
  pull-up follows the I3C port voltage. An external pull-up follows it only if it is tied to the
  port's VTARG pin (section 3.3).

| Supernova I3C HV port | Device | Required |
|---|---|---|
| SCL | SCL | required |
| SDA | SDA | required |
| GND | GND | required |
| VTARG | pull-up resistors, or the device I/O supply | required if the bus has external pull-ups |

### 3.3 Bus considerations

The I3C port has no pull-up on SCL, and SMBus needs one. Tie the SMBus pull-ups to the port's
VTARG pin, not to a fixed 3.3 V rail. VTARG follows `set_voltage`, so step 4 takes the pull-ups
from 3.3 V to 1.8 V with the bus. A pull-up to a fixed 3.3 V rail would hold the bus at 3.3 V
after step 4, above what a 1.8 V device accepts.

> **Caution:** a device that is not 3.3 V tolerant must not be on the bus during steps 1 to 3.

> **Caution:** only one controller on the bus.

## 4 Software setup

Install pyCosmicSDK from PyPI with the same Python that runs the script:

```
python -m pip install pycosmicsdk
```

Update the Supernova to firmware 4.6.0 or later with Mission Control.

## 5 Procedure

Run the script with the static address of each I3C device on the bus. The defaults are 3300 mV
for SMBus, 1800 mV for I3C, and SETDASA with dynamic addresses from 08h:

```
python smbus_to_i3c_daa.py --i3c-static 0x3A --daa setdasa
python smbus_to_i3c_daa.py --i3c-static 0x3A --daa entdaa
```

The output names each step. On the bench of section 6:

```
FW-4.6.2 controller | target FW-4.6.2
1. SMBus mode, bus at 3300 mV
2. DISEC to 7Eh: ACK, an I3C device is present
3. SMBus probe 08h-77h: 3Ah -> SMBus-only: none
4. Bus and pull-ups at 1800 mV
5. SETDASA: dynamic 08h, GETPID 0B0000000A01
```

The script stops after step 2 if nothing ACKs 7Eh, and after step 3 if an SMBus-only device
answers. In both cases the bus stays at the SMBus voltage. It exits with 0 when every assigned
device returned its PID.

To use the sequence in your own code, copy the `run` function: each step is a few lines and
uses only the calls in table 3.

Table: smbus_to_i3c_daa.py options

| Option | Default | Meaning |
|---|---|---|
| `--serial` | any | serial number (or prefix) of the controller Supernova |
| `--i3c-static` | required | static addresses of the I3C devices; any other SMBus answer counts as SMBus-only |
| `--daa` | `setdasa` | `setdasa` assigns one address per static address; `entdaa` lets the firmware assign every device |
| `--first-dynamic` | 0x08 | first dynamic address that SETDASA assigns |
| `--smbus-mv` | 3300 | bus voltage for steps 1 to 3 |
| `--i3c-mv` | 1800 | bus voltage for step 5 |
| `--settle-ms` | 10 | wait after the voltage change |
| `--emulate-target` | none | serial of a second Supernova that plays the I3C device at the first `--i3c-static` address |
| `--rounds` | 1 | run the sequence this many times and print the count that passed |

## 7 Troubleshooting

Table: Troubleshooting

| Symptom | Probable cause and action |
|---|---|
| Step 2 reports NACK with an I3C device on the bus | The device is not powered, or not at the SMBus voltage. Check `--smbus-mv` and the device supply. |
| Step 3 lists the I3C device as SMBus-only | Its static address is missing from `--i3c-static`. Add it. |
| Step 3 finds nothing, step 5 still works | The device does not answer SMBus reads at its static address. This does not affect the sequence. |
| Step 5 GETPID fails with `FW_I3C_NACK_ADDRESS` | The bus is still above the device's I/O voltage, or the device does not support the DAA method. Check that the pull-ups are tied to VTARG, or try the other `--daa`. |
| Bus still at 3.3 V after step 4 | External pull-ups to a fixed 3.3 V rail. Tie them to VTARG (section 3.3). |
